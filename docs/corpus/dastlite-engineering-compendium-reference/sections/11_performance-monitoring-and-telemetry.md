### Resource Utilization Metrics

Resource utilization metrics are a critical component of performance monitoring and telemetry in the dastlite system, providing actionable insights into how effectively the system leverages its computational and network resources during execution. These metrics are collected at multiple layers—process-level, thread-level, and system-level—to ensure comprehensive visibility into the operational efficiency of the tool. By tracking these metrics, dastlite enables users to identify bottlenecks, optimize resource allocation, and predict scalability limits. The metrics are captured in real-time using a combination of operating system APIs, profiling tools, and custom instrumentation, ensuring that they are both granular and accurate.

At the process level, dastlite employs standard Unix/Linux system calls such as `getrusage()` and `/proc` filesystem entries to monitor CPU time, memory usage, and I/O operations. The `getrusage(RUSAGE_SELF)` function provides detailed information about the CPU time consumed by the process and its children, while `/proc/self/status` offers insights into memory utilization, including resident set size (RSS), virtual memory size (VSZ), and page faults. These metrics are essential for understanding how much computational power the dastlite process is consuming during active scans. For example, a spike in CPU usage might indicate an increase in the number of concurrent requests being processed or the execution of complex scan rules. Similarly, a high RSS value could suggest that the tool is allocating excessive memory, potentially leading to memory contention on shared systems.

At the thread level, dastlite utilizes the `pthread` library and system-specific APIs such as `perf_event_open()` on Linux to monitor individual thread behavior. Each scanning thread in dastlite is instrumented to report its own CPU time, memory footprint, and I/O activity. This allows for fine-grained analysis of resource allocation across parallel execution paths. For instance, if one thread is consuming significantly more CPU than others, it may indicate an imbalance in workload distribution or the presence of a particularly resource-intensive scan rule. The use of `perf_event_open()` enables the collection of hardware-level metrics such as cache misses and branch mispredictions, which are crucial for identifying performance bottlenecks at the architectural level.

System-level resource utilization metrics are gathered through integration with the host operating system’s monitoring tools. On Linux, dastlite leverages `sysfs` and `/proc/diskstats` to track disk I/O operations, while `netstat` and `ip` commands provide insights into network throughput and latency. Additionally, dastlite uses `cgroup` (control groups) to monitor resource consumption at the container level, which is particularly relevant when running in orchestrated environments such as Kubernetes or Docker. By aggregating these metrics, dastlite provides a holistic view of how the tool interacts with the underlying infrastructure, enabling users to optimize both application and system-level performance.

The collection of these metrics is not limited to passive observation; dastlite also employs active instrumentation within its codebase. For example, when executing scan rules, dastlite logs the time taken for each rule to execute and the amount of memory allocated during that execution. This data is stored in a structured format, such as JSON or CSV, and can be visualized using tools like Grafana or Prometheus. These metrics are also used to generate alerts when thresholds are exceeded, allowing users to take proactive measures to mitigate resource exhaustion.

One of the key advantages of dastlite’s approach to resource utilization is its ability to correlate metrics across different layers. For instance, a high CPU usage in the process-level metrics might be linked to specific threads that are executing complex scan rules, which in turn could be associated with increased memory allocation or disk I/O operations. This correlation enables users to pinpoint the root cause of performance issues with greater precision. For example, if a particular scan rule is causing excessive CPU usage, users can optimize that rule or adjust the number of threads allocated to it.

In addition to capturing metrics during execution, dastlite also provides historical data for resource utilization. This allows users to analyze trends over time and identify patterns that may indicate long-term performance degradation. For instance, if memory usage increases steadily over multiple scan runs, it could indicate a memory leak in the tool or an inefficient use of memory by certain scan rules. Historical data is particularly useful when evaluating the impact of configuration changes or updates to the active-scan ruleset.

The integration of these metrics into dastlite’s telemetry system ensures that users have real-time visibility into resource utilization, enabling them to make informed decisions about system optimization. For example, if a particular scan is causing high disk I/O, users can adjust the scanning schedule or optimize the data being processed to reduce the load on the storage subsystem. Similarly, if network latency is affecting scan performance, users can configure the tool to use more efficient protocols or reduce the number of concurrent requests.

By combining process-level, thread-level, and system-level metrics with active instrumentation and historical analysis, dastlite provides a robust framework for monitoring resource utilization. This comprehensive approach not only helps in identifying performance bottlenecks but also enables users to optimize the tool’s operation within their specific infrastructure constraints. The ability to correlate these metrics across different layers of the system ensures that users can gain deep insights into how dastlite is performing and how it can be further optimized for efficiency and scalability.

In summary, resource utilization metrics in dastlite are collected through a combination of standard system calls, profiling tools, and custom instrumentation. These metrics are categorized at the process, thread, and system levels, providing granular insights into how the tool consumes computational and network resources. The integration of these metrics with active monitoring and historical analysis ensures that users have the necessary tools to optimize performance, identify bottlenecks, and predict scalability limits. ### Network Latency and Throughput Analysis

Network latency and throughput analysis are critical components of performance monitoring and telemetry in a distributed system like dastlite. These metrics provide insight into the efficiency of data transfer across the network, which directly impacts the speed and reliability of the DAST scan execution. To measure these parameters effectively, dastlite employs a combination of low-level network protocols, high-resolution timing mechanisms, and performance counters that are integrated into its core architecture.

At the foundation of latency and throughput analysis in dastlite is the use of the **TCP/IP stack**, which governs the transmission of data packets between nodes. The system leverages **Time-to-Live (TTL)** values and **Round-Trip Time (RTT)** measurements to assess network performance. RTT, in particular, is a key metric for understanding how quickly data traverses the network from the sender to the receiver and back. dastlite uses the **TCP Timestamp Option** to capture precise timestamps at both ends of the connection, enabling accurate RTT calculations. This feature is supported by the **IPv4 and IPv6 headers**, which include fields for timestamping and sequence numbering.

To further refine latency measurements, dastlite integrates with the **Linux `gettimeofday()` system call** and the **`clock_gettime()` function** with the `CLOCK_MONOTONIC` clock source. These mechanisms allow for sub-millisecond precision in timing events, ensuring that even minor variations in network performance are captured. For example, when a DAST scanner initiates a request to a target API endpoint, dastlite records the exact time of transmission and the time of receipt. The difference between these timestamps yields the RTT, which is then aggregated across all requests to provide an overall latency profile.

Throughput, on the other hand, measures the volume of data that can be transmitted over a network within a given period. dastlite calculates throughput by tracking the number of bytes transferred and the duration of the transfer. This is achieved through the use of **TCP window size** and **acknowledgment (ACK) packets**, which provide information about the amount of data successfully transmitted. The system also employs **bandwidth sampling techniques** to estimate the effective throughput of the network. For instance, dastlite can measure the rate at which data is received from a target API by analyzing the time intervals between successive ACKs and the size of the data segments being acknowledged.

To ensure that these metrics are consistent and reliable, dastlite implements **network interface-level counters** using the **libpcap** library and **DPDK (Data Plane Development Kit)** for high-performance packet capture. These tools allow dastlite to monitor traffic at the hardware level, providing granular insights into how data flows through the network. For example, by capturing packets at the **NIC (Network Interface Card)** level, dastlite can measure the actual data rate being transmitted and identify potential bottlenecks such as congestion or packet loss.

In addition to low-level network metrics, dastlite also incorporates **application-layer performance counters** to provide a more holistic view of throughput. These counters track the number of successful requests, the size of payloads, and the time taken to process each request. This data is collected using **gRPC metrics**, which are integrated into the DAST scanner's communication with the target API. By analyzing these metrics, dastlite can identify patterns in throughput that may indicate performance degradation or resource contention.

To further enhance the accuracy of latency and throughput analysis, dastlite employs **distributed tracing** using **OpenTelemetry**. This allows for end-to-end visibility into the network path taken by each request, from the DAST scanner to the target API and back. OpenTelemetry provides **span-based tracing**, where each request is represented as a series of spans that capture timing information at various stages of the request lifecycle. For example, a span may be created when the DAST scanner sends a request, another when the target API processes it, and yet another when the response is received. These spans are then aggregated to provide a detailed breakdown of latency and throughput across the entire network path.

The integration of OpenTelemetry with dastlite also enables **distributed tracing of backend services**, which is crucial for understanding how network performance impacts application behavior. For instance, if a particular API endpoint is experiencing high latency, dastlite can trace the request through the backend services to identify whether the delay is due to network congestion, database query timeouts, or other factors. This level of visibility allows for more targeted optimization efforts.

To ensure that latency and throughput metrics are captured consistently across different environments, dastlite uses **configurable sampling rates** and **adaptive measurement intervals**. These settings can be adjusted based on the workload and network conditions. For example, in a high-throughput environment, dastlite may reduce the sampling rate to minimize overhead while still capturing sufficient data for analysis. Conversely, in a low-throughput environment, it may increase the sampling rate to ensure that even minor variations in performance are detected.

Finally, dastlite leverages **SARIF (Static Analysis Results Interchange Format)** to emit telemetry data related to latency and throughput. This format allows for structured, machine-readable reports that can be integrated into CI/CD pipelines and monitoring systems. By embedding latency and throughput metrics within SARIF files, dastlite ensures that performance data is available for analysis alongside security findings, enabling a more comprehensive view of the system's health.

In summary, network latency and throughput analysis in dastlite are achieved through a combination of low-level network protocols, high-resolution timing mechanisms, and application-layer counters. The integration of tools like OpenTelemetry and libpcap provides end-to-end visibility into network performance, while configurable sampling rates ensure that metrics are captured efficiently. These techniques enable dastlite to deliver accurate, actionable insights into the performance of its distributed DAST scanning operations.
