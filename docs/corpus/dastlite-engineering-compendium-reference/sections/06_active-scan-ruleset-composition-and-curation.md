## 6. Active-Scan Ruleset Composition and Curation

### Rule Engine Architecture and Design

The Rule Engine Architecture and Design of dastlite's active-scan ruleset is a critical component that ensures the system can dynamically evaluate and execute a curated set of rules tailored to authenticated web and mobile API surfaces. At its core, the rule engine operates as a stateful, event-driven processing framework, designed to handle both synchronous and asynchronous interactions with the target application. This architecture is built upon a modular design principle, where each rule is encapsulated within a self-contained module, enabling scalability, maintainability, and extensibility. The engine leverages a combination of declarative and imperative programming paradigms to balance flexibility with performance, ensuring that rules can be composed, modified, and executed without significant overhead.

The rule engine is structured around a central processing pipeline, which consists of three primary stages: **rule parsing**, **execution context initialization**, and **rule execution**. During the **rule parsing phase**, each active-scan rule is deserialized from its serialized format (typically JSON or YAML) and transformed into an internal representation that the engine can interpret and execute. This phase involves validating the syntax of the rule, resolving dependencies, and compiling any embedded logic or conditions. For instance, a rule may define a set of HTTP requests to be sent, along with expected responses, and the parsing stage ensures that these components are correctly structured and compatible with the engine’s execution model.

The **execution context initialization** phase prepares the environment in which each rule will operate. This includes setting up variables, initializing stateful data structures, and configuring any required parameters such as authentication tokens, headers, or payloads. The context is dynamically generated based on the current crawl state and the specific authentication method being used (e.g., OAuth2, Basic Auth, API Key). For example, if a rule requires a bearer token, the engine will fetch the latest token from the authentication manager and inject it into the execution context before proceeding to the execution phase. This ensures that each rule runs with the correct credentials and contextual information, enabling accurate testing of authenticated endpoints.

The **rule execution** phase is where the actual scanning logic is applied. Each rule is executed as an independent unit, leveraging a combination of predefined templates and custom logic. The engine supports both **static** and **dynamic** rule execution models. Static rules are pre-defined and operate based on fixed patterns, such as checking for specific HTTP status codes or response headers. Dynamic rules, on the other hand, are more flexible and can adapt to runtime conditions. For instance, a dynamic rule might analyze the content of a response body to detect potential vulnerabilities, such as SQL injection or XSS, using regular expressions or machine learning-based pattern matching.

To ensure consistency and accuracy across all rules, the engine employs a **rule validation framework** that checks for syntactic correctness, semantic validity, and compatibility with the target application. This framework includes a set of predefined validation rules that are applied during the parsing phase. For example, a rule may be validated to ensure that all required HTTP methods (GET, POST, etc.) are correctly specified, and that any conditional logic (e.g., if-else statements) is properly structured. Additionally, the engine performs **type checking** on variables and parameters to prevent runtime errors. This validation process ensures that each rule is robust and can be executed without requiring additional runtime modifications.

The architecture also incorporates a **rule composition system**, which allows for the dynamic combination of multiple rules into cohesive scanning workflows. This system is built upon a **rule graph** model, where each node represents a rule or a set of rules, and edges represent dependencies or execution order. The rule graph is constructed during the parsing phase and is used to determine the sequence in which rules should be executed. For example, a group of rules may be organized into a workflow that first authenticates to the target application, then crawls its endpoints, and finally applies specific vulnerability checks. This compositional approach enables the engine to handle complex scanning scenarios while maintaining clarity and modularity.

To support extensibility, the rule engine is designed with a **plugin architecture** that allows for the addition of new rules or rule types without modifying the core engine. Each plugin is implemented as a self-contained module, which can be dynamically loaded at runtime. This modular design enables teams to contribute custom rules tailored to specific applications or security requirements. For instance, a plugin might be developed to support a proprietary API format or to detect a specific type of vulnerability unique to a particular ecosystem. The engine’s plugin system is based on a **service-oriented architecture**, where each plugin exposes a well-defined interface that the engine can invoke during execution.

The rule engine also includes a **rule optimization system** that identifies and eliminates redundant or overlapping rules to improve performance. This system uses static analysis techniques to detect rules that may produce duplicate findings or unnecessary network traffic. For example, if two rules are designed to check for the same vulnerability in different ways, the optimization system may merge them into a single, more efficient rule. This optimization is performed during the parsing and validation phases, ensuring that the final set of rules is both effective and resource-efficient.

In terms of execution efficiency, the rule engine employs **asynchronous processing** to handle multiple rules concurrently. This is achieved through an event-driven architecture, where each rule is executed as a separate task within a thread pool or an actor model. Asynchronous execution allows the engine to process multiple rules in parallel, significantly reducing scan time for large applications. For instance, while one rule is scanning for SQL injection vulnerabilities in one endpoint, another rule can be checking for XSS vulnerabilities in a different endpoint, all without blocking each other.

The engine also supports **custom execution contexts**, which allow users to define specific parameters or configurations for individual rules. This feature is particularly useful when dealing with complex applications that require tailored scanning strategies. For example, a custom context might specify a particular set of headers, query parameters, or authentication tokens that are required for a specific rule to function correctly. These contexts are stored as part of the rule’s metadata and are dynamically applied during execution.

To ensure accuracy and repeatability, the engine includes a **rule execution logging system** that records detailed information about each rule’s execution, including input parameters, HTTP requests and responses, and any findings detected. This logging is essential for debugging, auditing, and post-scan analysis. The logs are stored in a structured format, such as JSON or XML, and can be easily integrated with other tools for further processing or reporting.

Finally, the rule engine is designed to support **rule versioning**, allowing users to track changes to rules over time and ensure compatibility with different versions of the target application. Each rule is assigned a version number, and the engine can selectively apply specific versions based on the application’s current state. This feature is particularly important in environments where applications are frequently updated, as it ensures that the scanning process remains consistent and accurate across different deployment cycles.

In summary, the Rule Engine Architecture and Design of dastlite's active-scan ruleset is a sophisticated yet modular framework that enables efficient, accurate, and extensible vulnerability detection. By combining declarative and imperative paradigms, dynamic execution models, and a robust validation system, the engine ensures that each rule is executed in a consistent and reliable manner, while also supporting scalability and adaptability to evolving application landscapes.

### Rule Prioritization and Weighting Models

The foundation of an effective active-scan ruleset lies not only in its breadth but also in its precision—specifically, how individual rules are prioritized and weighted within the overall framework. Rule prioritization and weighting models serve as the backbone of intelligent rule selection, ensuring that the most impactful and relevant rules are executed first, while less critical ones are either deferred or excluded based on context. These models are essential for optimizing performance, reducing false positives, and aligning the scan with the specific goals of the target system.

At the core of rule prioritization is the concept of rule significance, which is determined by a combination of static metadata, historical data, and runtime behavior. Static metadata includes attributes such as the rule’s name, category, severity level, and origin (e.g., whether it was developed internally or sourced from an external repository). Historical data, on the other hand, encompasses past scan results, including how often a rule triggered a true positive, how frequently it produced false positives, and any user feedback or overrides applied over time. Runtime behavior introduces dynamic factors such as the current state of the target system, the presence of authentication tokens, and the response time of endpoints. These elements collectively form a multidimensional scoring system that assigns each rule a priority level.

One of the most widely adopted frameworks for rule prioritization is the **Rule Impact Score (RIS)**, which quantifies the potential impact of a rule based on its historical performance and contextual relevance. The RIS is calculated using a weighted formula that incorporates several factors: the rule’s historical true positive rate (TPR), false positive rate (FPR), and user feedback score (UFS). For example, a rule with a high TPR and low FPR would receive a higher RIS, indicating that it is both effective and reliable. Conversely, a rule with a high FPR and low TPR might be downgraded or excluded from the active-scan ruleset entirely. The UFS further refines this score by incorporating user feedback, such as manual overrides or suppression requests, which can either elevate or depress a rule’s priority based on its perceived value in specific contexts.

In addition to the RIS, **contextual weighting models** are employed to adjust rule priorities dynamically based on the target environment. These models consider factors such as the type of application being scanned (e.g., web app, mobile API, microservices), the presence of authentication mechanisms, and the expected behavior of endpoints. For instance, a rule that identifies SQL injection vulnerabilities might be prioritized higher in a web application with known SQL query patterns, while the same rule might be weighted lower in a mobile API that uses parameterized queries. This contextual adjustment ensures that rules are not applied uniformly across all environments but are instead tailored to the unique characteristics of each target system.

Another critical component of rule weighting is **rule dependency analysis**, which evaluates how individual rules interact with one another and how their execution order affects overall scan efficiency. Some rules may require specific conditions to be met before they can be executed, while others may generate false positives if applied in certain sequences. For example, a rule that detects cross-site scripting (XSS) might produce false positives if executed before a rule that identifies and suppresses benign script injections. Dependency analysis ensures that such interactions are accounted for, allowing the system to optimize the order of rule execution and minimize unnecessary overhead.

The **threshold-based prioritization model** is another mechanism used to determine which rules are included in the active-scan ruleset. This model defines a minimum threshold for a rule’s RIS or other scoring metrics, beyond which it is considered relevant and worth executing. Rules that fall below this threshold are either excluded or placed in a lower-priority queue. Thresholds can be static or dynamic; static thresholds are predefined based on historical data, while dynamic thresholds adjust in real-time based on the current scan context. For example, during a high-traffic period, the system might lower the threshold to include more rules that could detect transient vulnerabilities, whereas during low-traffic periods, it might raise the threshold to focus on more critical issues.

To further refine rule prioritization, **machine learning models** are increasingly being integrated into the active-scan framework. These models analyze large datasets of scan results, historical vulnerabilities, and user feedback to predict which rules are most likely to yield actionable findings. For instance, a supervised learning model trained on past scan data can identify patterns that correlate with high-quality vulnerability detections, allowing the system to prioritize rules based on these predictive insights. Reinforcement learning techniques are also being explored, where the system continuously learns from its interactions with the target environment, adjusting rule priorities in real-time based on feedback from previous scans.

In addition to these technical mechanisms, **user-defined prioritization policies** play a crucial role in shaping the active-scan ruleset. These policies allow administrators to specify custom criteria for rule selection, such as excluding certain types of rules based on organizational preferences or including rules that are known to be particularly effective in specific scenarios. For example, an organization might prioritize rules that detect insecure direct object references (IDOR) if it has a history of such vulnerabilities in its systems, while de-prioritizing rules related to outdated libraries if those libraries are already known to be secure in the current environment.

The integration of **rule weighting with scan performance metrics** is another key aspect of rule prioritization. By analyzing how each rule affects scan execution time and resource consumption, the system can balance the need for thoroughness with the constraints of performance. For instance, a rule that requires extensive payload generation or deep traversal of the application surface might be assigned a lower weight if the target system has limited bandwidth or processing power. Conversely, lightweight rules that generate minimal overhead might be given higher priority, especially in environments where rapid feedback is critical.

Finally, **rule prioritization and weighting models** are not static; they evolve over time as new vulnerabilities emerge, scanning technologies advance, and user feedback is incorporated. Continuous learning mechanisms ensure that the system adapts to these changes, maintaining the relevance and effectiveness of the active-scan ruleset. For example, if a new vulnerability class is identified in a widely used framework, the system can automatically adjust the weights of related rules to reflect their increased importance, ensuring that the ruleset remains up-to-date and aligned with the latest security threats.

In summary, rule prioritization and weighting models are essential for creating an intelligent, adaptive active-scan ruleset that balances precision, performance, and relevance. By leveraging a combination of static metadata, historical data, contextual factors, machine learning, and user-defined policies, these models ensure that the most impactful rules are executed first, while less critical ones are either deferred or excluded. This dynamic approach not only enhances the effectiveness of the active-scan process but also aligns it with the specific needs and constraints of the target environment.

These conditions are typically expressed in terms of HTTP methods, request paths, response codes, headers, and payloads, and they form the logical foundation upon which rule execution is based. For example, a rule designed to detect insecure HTTP methods may trigger only when a `POST` request is made to a specific endpoint that returns a `200 OK` response with a `Content-Type` of `application/json`. Such conditions are often expressed using a combination of static and dynamic criteria, including predefined patterns, regex matches, and contextual metadata. These conditions are evaluated in real-time during the crawl, allowing the DAST runner to dynamically decide whether a rule is applicable at any given moment.

The execution context of an active scan rule refers to the environment in which the rule operates, encompassing factors such as the current request path, authentication state, session cookies, and the sequence of prior requests. These contextual elements are critical for determining the relevance and accuracy of rule triggers. For instance, a rule that detects SQL injection may only trigger when a `GET` request is made to an endpoint that accepts query parameters and returns a `200 OK` response with a `Content-Type` of `text/html`. The execution context also includes the presence or absence of authentication tokens, which can influence whether certain endpoints are accessible during the scan. This contextual awareness ensures that rules are applied only when they have a high probability of yielding meaningful results, reducing false positives and improving overall scan efficiency.

Rule trigger conditions are often implemented using a combination of static and dynamic evaluation mechanisms. Static conditions are typically defined in the rule's metadata and include fixed parameters such as HTTP methods, response codes, or specific headers. These conditions are evaluated against the current request and response data to determine whether the rule should be executed. For example, a rule that detects insecure HTTP methods may have a static condition that requires the `POST` method and a `Content-Type` of `application/json`. Dynamic conditions, on the other hand, are based on runtime data such as the presence of specific query parameters, the content of the response body, or the state of the authentication session. These dynamic conditions are often implemented using regex patterns or custom logic that can adapt to varying request and response structures.

The implementation of rule trigger conditions is typically supported by a combination of internal and external mechanisms. Internal mechanisms include the DAST runner's built-in rule engine, which processes each request and response to evaluate whether the current context satisfies the rule's trigger conditions. This engine may use a rule-specific parser that extracts and evaluates conditions from the rule's metadata, applying them in real-time during the crawl. External mechanisms, such as the integration with the DAST runner's configuration system, allow for the dynamic loading of rules and their associated conditions based on the current scan environment. For example, a rule may be configured to only execute when certain authentication credentials are present, or when specific endpoints are accessible during the crawl.

Rule trigger conditions are often expressed using a combination of logical operators and conditional expressions. These expressions can be as simple as checking whether a particular HTTP method is used, or as complex as evaluating multiple response headers and body content for specific patterns. For example, a rule designed to detect insecure redirects may have a condition that checks for a `302 Found` response code and a `Location` header pointing to an external domain. Such conditions are typically implemented using a combination of static and dynamic evaluation techniques, ensuring that the rule is triggered only when the specified criteria are met. This approach allows for precise control over when a rule is executed, minimizing unnecessary scans and improving overall performance.

The evaluation of rule trigger conditions is closely tied to the DAST runner's crawling and scanning process. As the runner traverses the web or mobile API surface, it continuously evaluates each request and response against the active scan ruleset. This evaluation is performed in real-time, ensuring that rules are only executed when their conditions are met. For example, a rule that detects insecure HTTP methods may be evaluated after each `GET` or `POST` request, checking whether the current request path and method match the rule's static conditions. If the conditions are satisfied, the rule is executed, generating a test payload and analyzing the response for potential vulnerabilities.

The execution context of an active scan rule also includes the state of the authentication session, which can influence whether certain endpoints are accessible during the scan. For instance, a rule designed to detect insecure endpoints may only be triggered when the current request is authenticated, as unauthenticated endpoints may not require the same level of scrutiny. This contextual awareness ensures that rules are applied only when they are most relevant, reducing the likelihood of false positives and improving the accuracy of the scan. The DAST runner's configuration system allows for the dynamic adjustment of rule trigger conditions based on the current authentication state, enabling more precise and targeted scanning.

Rule trigger conditions may also be influenced by the sequence of prior requests and responses. For example, a rule that detects cross-site scripting (XSS) vulnerabilities may only be triggered when a particular request path is accessed after a successful login, as this indicates that the session is authenticated. This sequential dependency is often implemented using a combination of state tracking and conditional logic, ensuring that rules are executed in the correct context. The DAST runner's internal state management system tracks the current authentication status and other contextual factors, allowing for dynamic adjustment of rule trigger conditions based on the scan's progression.

The implementation of rule trigger conditions also involves the use of metadata and configuration files that define the specific criteria for each rule. These files are typically structured in a way that allows for easy parsing and evaluation by the DAST runner's rule engine. For example, a rule may have a metadata file that specifies static conditions such as HTTP methods and response codes, while dynamic conditions are defined using regex patterns or custom logic. This modular approach enables the DAST runner to efficiently evaluate each rule's trigger conditions, ensuring that only relevant rules are executed during the scan.

In addition to static and dynamic conditions, rule trigger conditions may also include temporal constraints, such as the time of day or the duration of the scan. These constraints are often used to optimize scanning efficiency by executing certain rules only during specific periods when they are most likely to yield meaningful results. For example, a rule designed to detect memory leaks may be configured to execute only during the first 10 minutes of the scan, as this is when memory usage is typically highest. Temporal constraints are implemented using a combination of internal timers and external configuration parameters, allowing for flexible and context-aware rule execution.

The evaluation of rule trigger conditions is further enhanced by the use of metadata and contextual data that describe the current state of the scan. This data includes information such as the current request path, the authentication status, and the sequence of prior requests. By incorporating this contextual data into the rule evaluation process, the DAST runner can make more informed decisions about whether a rule should be executed. Overall, the combination of static and dynamic conditions, along with contextual data and temporal constraints, enables the DAST runner to accurately evaluate when an active scan rule should be executed. This precise control over rule execution ensures that each rule is applied only when it is most relevant, improving the accuracy and efficiency of the scan. By leveraging these mechanisms, the DAST runner can effectively identify vulnerabilities while minimizing unnecessary scans and false positives.

### Rule Output Normalization and Deduplication

Rule Output Normalization and Deduplication is a foundational process in the active-scan ruleset composition and curation pipeline of dastlite. This phase ensures that the output from multiple active-scan rules is standardized, making it easier to parse, analyze, and integrate with downstream tools such as static analysis platforms or security orchestration systems. The normalization process involves structuring the scan results into a consistent format, while deduplication eliminates redundant findings, reducing noise and improving the precision of the final output.

At the core of this process is the SARIF (Structured Assertion Result Interpretation Format) standard, which serves as the common language for representing software security findings. dastlite leverages SARIF to ensure that all active-scan rules produce outputs in a uniform structure. Each rule is configured to emit findings as SARIF records, containing standardized fields such as `ruleId`, `message`, `location`, and `codeSnippet`. This standardization allows for seamless integration with tools like Azure DevOps, GitHub Advanced Security, and other security platforms that support SARIF. The use of SARIF also facilitates the inclusion of metadata about each finding, including severity levels, confidence scores, and remediation guidance.

The normalization process begins with the transformation of raw scan results into SARIF-compliant records. Each active-scan rule is responsible for generating these records in a structured format. For example, a rule that detects exposed database credentials will generate a SARIF record with the `ruleId` set to "exposed-database-credentials", a message describing the finding, and a location pointing to the specific endpoint or API call where the credential was found. This approach ensures that all findings are represented in a consistent manner, regardless of the rule's implementation details.

To further enhance normalization, dastlite employs a centralized configuration file for active-scan rules. This file defines common properties such as `outputFormat`, `severityMapping`, and `deduplicationKey`. The `outputFormat` field specifies whether the rule should emit findings in SARIF or another format, while `severityMapping` allows for mapping rule-specific severity levels to a standardized scale (e.g., low, medium, high). The `deduplicationKey` is used to identify unique findings based on specific attributes such as URL, HTTP method, and request body. This key is crucial for the deduplication process, as it ensures that identical findings are grouped together and only one instance is retained in the final output.

The deduplication process is implemented through a combination of rule-specific logic and centralized normalization mechanisms. Each active-scan rule is responsible for generating findings, but it also includes logic to detect and eliminate duplicates within its own scope. For example, a rule that scans for SQL injection vulnerabilities may include logic to check whether the same vulnerability has been reported multiple times on the same endpoint using the same payload. This internal deduplication helps reduce the volume of findings before they are passed to the normalization stage.

However, internal deduplication is not sufficient to address all cases of duplication, especially when findings are generated by different rules or across different scan sessions. To handle these scenarios, dastlite employs a centralized deduplication module that operates on the normalized SARIF records. This module uses the `deduplicationKey` defined in each rule's configuration to group findings and determine whether they are duplicates. The key is typically composed of attributes such as the URL, HTTP method, request body, and response code, ensuring that findings with identical characteristics are treated as duplicates.

The deduplication process also takes into account the context in which a finding was generated. For example, two different rules may report a vulnerability on the same endpoint but with slightly different descriptions or severity levels. In such cases, the centralized deduplication module evaluates the similarity of the findings and decides whether to merge them or retain both as separate entries. This evaluation is based on factors such as the `ruleId`, `message`, and `location` fields in the SARIF record, ensuring that the final output remains accurate and actionable.

One of the key challenges in deduplication is handling variations in the way findings are reported. For instance, a rule may generate a finding with a specific message, while another rule may report the same vulnerability with a slightly different phrasing. To address this, dastlite includes a normalization phase that standardizes the message content for each finding. This phase uses natural language processing (NLP) techniques to identify synonyms and rephrase messages into a consistent format. For example, a message such as "Potential SQL injection detected" may be standardized to "SQL injection vulnerability found," ensuring that similar findings are recognized as duplicates.

In addition to message normalization, dastlite also employs a heuristic-based approach for deduplication. This approach involves analyzing the similarity of findings based on their `location` and `codeSnippet` fields. By comparing these fields across different SARIF records, the deduplication module can identify findings that are likely to be duplicates, even if they were generated by different rules. For example, two rules may report a vulnerability on the same endpoint using the same payload, but with slightly different descriptions. The heuristic-based approach ensures that these findings are grouped together and only one instance is retained in the final output.

The deduplication process also includes a mechanism for retaining the most relevant finding when multiple duplicates exist. This mechanism evaluates the severity level, confidence score, and remediation guidance associated with each finding. For example, if two findings are reported on the same endpoint but with different severity levels, the one with the higher severity is retained as the primary finding, while the other is marked as a duplicate. This approach ensures that the final output includes only the most critical findings, improving the precision of the scan results.

To further enhance deduplication, dastlite incorporates a versioning system for active-scan rules. This system allows for tracking changes in rule behavior over time, ensuring that findings from different versions of the same rule are properly handled. For example, if a rule is updated to include additional detection logic, the deduplication module can differentiate between findings generated by the old and new versions of the rule, preventing false positives or redundant entries.

In addition to rule-specific deduplication, dastlite also includes a global deduplication phase that operates across all scan sessions. This phase uses a centralized database to store historical findings, allowing for the detection of duplicates across different scans. For example, if a vulnerability was previously reported on an endpoint during a previous scan, the global deduplication module can identify it as a duplicate in a subsequent scan, reducing the need for manual review and improving the efficiency of the process.

The combination of rule-specific and centralized deduplication mechanisms ensures that dastlite's active-scan ruleset produces high-quality, consistent results. By normalizing findings into a standardized format and eliminating duplicates through both internal and external mechanisms, dastlite ensures that the final SARIF output is accurate, actionable, and easy to integrate with downstream tools. This process not only improves the reliability of the scan results but also enhances the overall efficiency of the security testing workflow.

### Rule Maintenance and Versioning Strategies

Rule maintenance and versioning strategies are fundamental to ensuring the reliability, consistency, and evolution of an active-scan ruleset in a headless, config-as-code DAST runner. These strategies must address the lifecycle of each rule—from initial creation through continuous refinement, deprecation, and eventual retirement—while maintaining compatibility with the broader system architecture and runtime environment. A well-structured approach to rule maintenance ensures that the ruleset remains both effective and manageable over time, adapting to new security threats, changes in application behavior, and evolving tooling requirements.

At the core of rule maintenance is version control. Each active-scan rule must be associated with a version identifier, typically a semantic version (SemVer) string such as `1.2.3`. This allows for precise tracking of changes, dependencies, and compatibility across different environments. Version control is not merely an organizational convenience; it is a critical mechanism for managing the evolution of rules without disrupting ongoing scans or introducing unintended side effects. For example, when a rule is updated to fix a false positive or improve detection accuracy, the version number is incremented, and the change is logged in a changelog or commit message. This ensures that all stakeholders—developers, security engineers, and operators—can understand the impact of each update.

In practice, the use of Git repositories for storing active-scan ruleset components provides a robust infrastructure for version control. Each rule is stored as a separate file or module within the repository, with associated metadata such as author, date, and dependencies. This structure enables developers to track the history of each rule, identify when it was last modified, and understand the rationale behind specific changes. For instance, a rule that detects SQL injection might have undergone multiple iterations, with each version addressing new attack vectors or false positives. By maintaining a clear version history, teams can quickly roll back to a previous version if an update introduces unexpected behavior.

Versioning also plays a crucial role in ensuring compatibility between rules and the DAST runner itself. The DAST runner must be able to interpret and execute rules based on their version numbers, which may involve parsing versioned metadata or applying specific transformations. For example, a rule that uses a deprecated API might be marked with a version flag indicating that it is no longer supported, allowing the runner to skip or warn about its usage in future scans. This mechanism ensures that the ruleset remains aligned with the capabilities of the DAST runner and avoids runtime errors caused by mismatched versions.

In addition to versioning, rule maintenance requires a structured approach to dependency management. Each rule may depend on other rules, external libraries, or configuration files, and these dependencies must be explicitly defined and versioned. This allows for deterministic execution of the ruleset, where each component is known to be compatible with the others. For instance, a rule that performs multi-step validation might depend on a base rule for initial input sanitization. By specifying the exact versions of these dependencies, teams can ensure that changes to one rule do not inadvertently affect others.

The process of maintaining and versioning rules is further enhanced by automated tools and CI/CD pipelines. These systems can be configured to run tests, linting checks, and compatibility validations whenever a rule is updated. For example, a CI pipeline might execute a suite of unit tests to verify that a rule behaves as expected under various input conditions. If the tests pass, the rule is tagged with a new version and pushed to the repository. This automation not only reduces the risk of human error but also ensures that the ruleset remains robust and up-to-date.

Another critical aspect of rule maintenance is the management of deprecation cycles. Rules that are no longer effective or have been superseded by newer versions must be marked for deprecation and eventually removed from the ruleset. This process involves identifying outdated rules, documenting their reasons for deprecation, and providing a timeline for their retirement. For instance, a rule that detects an old vulnerability might be deprecated once a new, more comprehensive rule is introduced. The deprecation process ensures that the ruleset remains lean and focused on relevant security concerns, without unnecessary bloat.

To support deprecation, the DAST runner can be configured to handle deprecated rules in specific ways. For example, when a deprecated rule is encountered during a scan, the runner might issue a warning or log a message indicating that the rule is no longer recommended for use. This provides visibility into the state of the ruleset and helps teams prioritize the removal of deprecated rules. Over time, deprecated rules are systematically removed from the repository, ensuring that the active-scan ruleset remains current and efficient.

Rule maintenance also involves continuous integration with external sources of security intelligence. For example, a ruleset might incorporate rules from open-source projects such as OWASP ZAP or commercial tools like Contrast Security. These external rules must be versioned and integrated into the internal ruleset in a way that maintains compatibility and consistency. This may involve using versioned dependencies or pull requests to merge changes from external repositories into the internal ruleset. By maintaining a clear lineage of rules, teams can ensure that the ruleset remains aligned with the latest security best practices.

Finally, rule maintenance strategies must account for the dynamic nature of web applications and APIs. As applications evolve, new endpoints are added, existing ones are modified, and deprecated ones are removed. This necessitates periodic reviews of the ruleset to ensure that it continues to cover all relevant attack surfaces. For example, a rule that targets a specific API endpoint might need to be updated if the endpoint is restructured or renamed. These updates are versioned and tracked, ensuring that the ruleset remains aligned with the application's current state.

In summary, rule maintenance and versioning strategies form the backbone of an effective active-scan ruleset in a headless, config-as-code DAST runner. By leveraging version control, dependency management, automated testing, and deprecation cycles, teams can ensure that their ruleset remains reliable, efficient, and aligned with evolving security requirements. These strategies not only enhance the accuracy and effectiveness of active scans but also provide a structured framework for continuous improvement and adaptation.

### Rule Integration with SARIF Emission Pipelines

The integration of active-scan rulesets with SARIF emission pipelines is a critical component in the architecture of dastlite, ensuring that findings are not only generated but also structured, transmitted, and consumed in a consistent, machine-readable format. At the core of this integration lies the seamless transformation of rule execution results into SARIF-compliant artifacts, which are then injected into broader software security and DevOps pipelines. This process is underpinned by a combination of rule execution semantics, metadata mapping, and pipeline orchestration mechanisms that ensure fidelity, traceability, and scalability.

To begin, the active-scan ruleset in dastlite is composed of modular, declarative rules that define conditions for detecting vulnerabilities or misconfigurations during crawling. Each rule is associated with a set of predefined actions, such as triggering a scan, collecting evidence, and generating a finding. These findings are initially stored in an internal representation format, often a JSON-like structure that captures the context, severity, and remediation details of each vulnerability. The challenge lies in converting this internal representation into the structured, standardized format required by SARIF.

This conversion process is facilitated by a rule-specific emitter module, which maps the internal finding data to the corresponding SARIF schema elements. For example, the `ruleId` field in SARIF is mapped to the unique identifier of the active-scan rule, while the `message` and `location` fields are populated based on the extracted evidence from the scan. Additionally, metadata such as the tool name, version, and configuration parameters are embedded into the SARIF artifact to ensure contextual completeness. This mapping is not arbitrary but rather defined through explicit schema definitions that align with the specific structure of dastlite's active-scan ruleset.

The SARIF emission pipeline in dastlite is designed as a series of interconnected components that handle the transformation, aggregation, and transmission of findings. The first stage involves the rule emitter module, which generates a raw SARIF document from the internal finding data. This document is then passed to a deduplication module that ensures findings are uniquely identified based on their location, rule ID, and other relevant attributes. Deduplication is essential to avoid redundant findings in the final SARIF output, particularly when multiple rules may produce overlapping results.

Once deduplicated, the SARIF artifact is enriched with additional metadata, such as timestamps, scan context, and integration-specific headers, which are required for downstream processing. This enrichment is performed by a metadata injector module that leverages predefined templates and configuration parameters to populate the necessary fields. The enriched SARIF document is then serialized into a standardized format, typically JSON, and transmitted to the next stage of the pipeline.

The final stage of the SARIF emission pipeline involves integration with external tools and platforms that consume SARIF artifacts. This is achieved through a set of predefined connectors that support common DevOps and security tools such as GitHub Actions, Azure DevOps, and SonarQube. These connectors are designed to accept the SARIF document and either directly ingest it into the target system or transform it into a format compatible with the system's requirements. For example, when integrating with GitHub Actions, the SARIF document may be converted into a JSON payload that is then used to trigger a workflow or update a security dashboard.

The integration of active-scan rulesets with SARIF emission pipelines is further enhanced by the use of configuration-as-code principles. The mapping between internal findings and SARIF elements is defined through a set of declarative configuration files, which are version-controlled and managed alongside the active-scan ruleset. These configuration files specify how each rule's output should be transformed into SARIF, ensuring consistency across different environments and deployment scenarios. For instance, a configuration file might define how a specific rule's `message` field should be mapped to the `shortMessage` field in SARIF, or how location information should be structured based on the URL and endpoint of the scanned resource.

This configuration-driven approach allows for flexibility and extensibility, enabling teams to customize the SARIF emission process without modifying the core rule execution logic. It also facilitates the reuse of rule definitions across different projects and environments, ensuring that findings are consistently formatted and interpreted across the organization. Furthermore, the use of configuration-as-code enables automated testing and validation of the SARIF emission pipeline, ensuring that any changes to the ruleset or mapping configurations are thoroughly tested before deployment.

Another key aspect of this integration is the ability to support multiple SARIF versions and extensions, allowing dastlite to adapt to evolving standards and tooling requirements. The SARIF emission pipeline is designed with version negotiation capabilities, enabling it to generate SARIF artifacts in the format required by the downstream tools. For example, if a downstream system requires SARIF 2.1.0, the pipeline will ensure that the generated artifact adheres to this version's schema, while also including any necessary extensions or custom fields that may be supported by the target system.

The integration of active-scan rulesets with SARIF emission pipelines is also enhanced by the use of event-driven architecture principles, allowing for real-time processing and streaming of findings. Instead of generating a single SARIF artifact at the end of a scan, dastlite can emit findings incrementally as they are detected, enabling immediate feedback and integration with continuous monitoring systems. This approach is particularly useful in large-scale environments where scans may take extended periods to complete, and real-time visibility into findings is critical for rapid remediation.

To further illustrate this process, consider the case of a rule that detects insecure HTTP endpoints during a web crawl. As the crawler discovers an endpoint using HTTP instead of HTTPS, the rule triggers a finding, which is then mapped to a SARIF artifact by the emitter module. The emitter module ensures that the `ruleId` field corresponds to the unique identifier of the rule, while the `message` field includes a description of the vulnerability, such as "Insecure HTTP endpoint detected." The location information is populated with the URL of the endpoint, and any additional evidence, such as the HTTP response code or headers, is included in the `location` and `codeFlows` fields of the SARIF artifact. This artifact is then passed to the deduplication module, which checks for existing findings with the same rule ID and location before finalizing the SARIF document.

The integration of active-scan rulesets with SARIF emission pipelines thus represents a well-defined, structured process that ensures the accurate transformation of scan results into standardized, consumable artifacts. By leveraging configuration-as-code principles, event-driven architecture, and schema-driven mapping, dastlite enables seamless integration with existing security and DevOps pipelines, ensuring that findings are not only generated but also effectively utilized for continuous improvement and risk mitigation.
