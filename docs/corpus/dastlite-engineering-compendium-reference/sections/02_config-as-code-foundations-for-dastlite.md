### YAML Grammar and Structure

The YAML grammar and structure in dastlite are designed to provide a declarative, human-readable, and machine-parsable configuration format that aligns with the principles of config-as-code. At its core, YAML (YAML Ain't Markup Language) is a superset of JSON, but it introduces additional features such as indentation-based syntax, inline collections, and anchors, which make it particularly well-suited for defining structured data in a concise and expressive manner. In the context of dastlite, YAML serves as the primary interface between the user and the system, allowing developers to define scan configurations, rulesets, authentication mechanisms, and output formats with clarity and precision.

The foundation of the YAML structure in dastlite is built upon a hierarchical key-value model, where each configuration block represents a specific component of the scanning process. This hierarchical approach enables users to organize complex configurations into logical sections, such as `targets`, `rulesets`, `authentication`, and `output`. Each of these sections contains key-value pairs that define the parameters for their respective components. For example, the `targets` section might contain a list of URLs or endpoints to be scanned, while the `rulesets` section specifies which active scan rules should be applied during the scan.

The YAML syntax in dastlite is designed to be both flexible and unambiguous. Indentation is used to denote the level of nesting within the configuration hierarchy, with each level requiring consistent indentation (typically two spaces). This ensures that the structure remains readable and maintainable, even for large and complex configurations. Additionally, YAML supports inline collections using hyphens (`-`) and key-value pairs using colons (`:`), which allows for the definition of lists and maps within a single line. For instance, a list of target URLs can be defined as:

```yaml
targets:
  - https://example.com
  - https://api.example.com/v1
```

This concise syntax not only reduces the amount of boilerplate required but also enhances readability by visually grouping related items together. Furthermore, YAML's support for anchors and aliases enables users to define reusable components within their configuration files. Anchors are defined using the `&` symbol, and aliases are referenced using the `*` symbol. This feature is particularly useful in dastlite for defining common configurations, such as authentication credentials or rule sets, that can be referenced across multiple targets or scan configurations.

In addition to its syntactic features, YAML's semantic structure plays a critical role in ensuring the correctness and consistency of dastlite configurations. The use of keys and values allows for the precise definition of parameters, with each key representing a specific configuration option and its corresponding value defining the desired behavior. For example, the `authentication` section might include a key such as `type`, which specifies whether the scan should use basic authentication, token-based authentication, or another method. The value associated with this key would then define the specific parameters required for that authentication type, such as username, password, or API key.

The YAML structure also supports nested configurations, allowing users to define complex relationships between different components of the scanning process. For instance, a `target` might have multiple `rulesets` associated with it, each of which can be configured with specific parameters. This nested structure is achieved through indentation and the use of subkeys, enabling users to create highly granular and customizable configurations. An example of this would be:

```yaml
targets:
  - url: https://example.com
    rulesets:
      - name: "sql-injection"
        enabled: true
        parameters:
          max_depth: 3
          timeout: 10
```

Here, the `rulesets` section is nested under the `targets` section, and each rule set is defined with its own set of parameters. This level of detail allows users to fine-tune the behavior of specific rules within a given target, ensuring that the scan is both comprehensive and efficient.

Another important aspect of the YAML grammar in dastlite is its support for comments, which are denoted by the `#` symbol. Comments provide a means of documenting the configuration, explaining the purpose of specific keys or values, and offering guidance on best practices. This feature is particularly valuable in larger configurations where clarity and maintainability are essential. For example:

```yaml
# Define the primary target for the scan
targets:
  - url: https://example.com
    # Enable SQL injection rules with a maximum depth of 3
    rulesets:
      - name: "sql-injection"
        enabled: true
        parameters:
          max_depth: 3
```

In this example, comments are used to clarify the purpose of the `max_depth` parameter, ensuring that future users or maintainers of the configuration can understand the rationale behind the chosen settings. This documentation capability enhances the usability and longevity of dastlite configurations.

The YAML structure also includes support for multi-line strings, which is particularly useful for defining complex parameters or descriptions within the configuration. Multi-line strings are denoted by using a pipe (`|`) or a greater-than sign (`>`) at the beginning of a line. For instance:

```yaml
description: |
  This scan targets the example.com domain and includes a curated set of active scan rules to identify potential vulnerabilities.
```

This feature allows for the inclusion of detailed descriptions or instructions within the configuration, making it easier to understand the intent behind specific settings.

In conclusion, the YAML grammar and structure in dastlite provide a robust and flexible framework for defining scan configurations. By leveraging the features of YAML, such as indentation-based syntax, inline collections, anchors, and comments, users can create precise, maintainable, and expressive configurations that align with the principles of config-as-code. The hierarchical key-value model, combined with the ability to define nested structures and reuse components through anchors, ensures that dastlite configurations are both powerful and intuitive. These features not only enhance the usability of the system but also contribute to the overall efficiency and reliability of the scanning process.

The injection of environment variables is not merely a syntactic convenience but a strategic design choice that aligns with the principles of infrastructure as code (IaC) and devops automation.

The primary mechanism for environment variable injection in dastlite is based on the `env` directive within the configuration schema, which allows for the reference of external variables defined at runtime. These variables can originate from multiple sources, including operating system environment variables, secret management systems like HashiCorp Vault or AWS Secrets Manager, and custom variables passed via command-line arguments or process environments. The injection process is governed by a hierarchical resolution strategy: first, the configuration file attempts to resolve any `env` references using the local process environment; if not found, it proceeds to query external secret stores or other designated sources. This layered approach ensures that dastlite can operate in both development and production environments with minimal configuration overhead.

One of the key advantages of this injection model is its support for conditional execution based on environment-specific parameters. For instance, a dastlite scan configuration might include a rule set that is only activated when the `ENVIRONMENT` variable is set to `production`. This allows for fine-grained control over which rules are executed, reducing false positives in development environments while ensuring comprehensive coverage in production. The resolution of such conditional variables is handled by the dastlite runtime engine, which evaluates the environment variables at configuration load time and applies the appropriate logic to the scan execution plan.

The injection of environment variables also plays a critical role in managing authentication credentials for the target application or API surface. Instead of hardcoding sensitive information like usernames, passwords, or API keys directly into the configuration files, dastlite allows these values to be injected dynamically. For example, the `AUTH_USERNAME` and `AUTH_PASSWORD` variables can be sourced from a secret store, ensuring that credentials are not exposed in plain text within the configuration. This approach aligns with best practices for secure configuration management and reduces the risk of credential leakage during development or testing.

In addition to authentication, environment variables enable the customization of scan behavior based on runtime conditions. For instance, the `SCAN_DEPTH` variable can be used to control how deep the crawler explores the application’s API surface, allowing for more aggressive scans in production environments and more conservative scans in staging or test environments. Similarly, the `MAX_REQUESTS` variable can be adjusted to limit the number of HTTP requests made during a scan, preventing resource exhaustion in high-traffic applications. These variables are injected into the configuration at runtime, ensuring that the scan adapts dynamically to the specific context in which it is executed.

The injection process also supports the use of placeholders within the configuration files, which are replaced with actual values during runtime. For example, a `TARGET_URL` variable might be defined as `https://{{TARGET_HOST}}/api/v1`, where the `TARGET_HOST` variable is injected from an external source. This mechanism allows for greater flexibility in defining scan targets, as the same configuration file can be reused across different environments by simply changing the values of the injected variables. The dastlite runtime engine ensures that all placeholders are correctly resolved before the scan execution begins, preventing errors related to missing or malformed configuration data.

Another important aspect of environment variable injection is its integration with external tools and services. This allows for centralized log management and monitoring, which is essential in distributed or microservices-based architectures. Similarly, the injection of variables related to reporting tools enables dastlite to generate scan results in various formats, such as SARIF, JSON, or CSV, depending on the environment’s requirements.

The use of environment variables also facilitates the implementation of feature flags within the dastlite configuration. These flags can be used to enable or disable specific features, such as the inclusion of certain active scan rules, based on runtime conditions. For example, the `ENABLE_ADVANCED_RULES` variable can be set to `true` in a production environment to trigger more sophisticated scan logic, while being set to `false` in a development environment to reduce scan time and resource consumption. This level of configurability ensures that dastlite can be tailored to meet the specific needs of different deployment scenarios.

In addition to these practical benefits, the injection of environment variables enhances the portability and reusability of dastlite configurations across different platforms and environments. By abstracting sensitive or context-specific data into variables, the configuration files remain clean and focused on defining the scan strategy rather than containing runtime-specific details. This separation of concerns makes it easier to maintain and version control the configuration files, as changes to environment variables do not require modifications to the core scan logic.

The dastlite runtime engine also includes a validation mechanism for environment variables, ensuring that all required variables are present and correctly formatted before the scan begins. If an environment variable is missing or malformed, the engine raises an error, preventing the scan from executing with incomplete or incorrect data. This validation process helps catch configuration errors early, reducing the risk of runtime failures and improving the overall reliability of the dastlite system.

Finally, the injection of environment variables in dastlite supports the use of dynamic values for scan parameters such as timeouts, retry policies, and connection limits. In summary, environment variables and injection are essential components of dastlite’s config-as-code foundation, enabling dynamic and context-aware execution of the DAST runner. This emitter operates on a model where each scan result—whether it be a vulnerability, an information leak, or a misconfiguration—is mapped to a corresponding SARIF **result** object. The mapping is governed by a set of rules defined in the **dastlite configuration**, which allows users to customize the structure and content of the emitted SARIF file. Another important aspect of the SARIF generation configuration is the **integration with external tools and platforms**.
