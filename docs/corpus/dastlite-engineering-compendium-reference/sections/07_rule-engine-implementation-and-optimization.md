### Rule Matching Architecture

The rule matching architecture within dastlite's rule engine is a meticulously designed system that ensures efficient, accurate, and scalable application of active-scan rules to authenticated web and mobile-API surfaces. At its core, this architecture employs a combination of deterministic pattern matching, dynamic rule evaluation, and context-aware filtering to align the vast array of potential vulnerabilities with the specific characteristics of each target system. The design leverages a layered approach, where each layer addresses a distinct aspect of the rule application process—rule parsing, context extraction, pattern evaluation, and result aggregation—ensuring that the engine can adapt to both static and dynamic environments without sacrificing performance or precision.

The first layer of the rule matching architecture is the **rule parsing and normalization** phase. Every active-scan rule is defined in a structured format, typically using a domain-specific language (DSL) that encapsulates the conditions under which a vulnerability might be triggered. These rules are parsed into an internal representation, such as an abstract syntax tree (AST), which allows for efficient traversal and evaluation during runtime. For example, a rule might define a specific HTTP method, a particular endpoint path, and a set of expected response headers or body content. During parsing, the engine normalizes these conditions by resolving any references to predefined patterns, such as regular expressions or XPath queries, ensuring that each rule is in a consistent and executable form.

Once the rules are parsed and normalized, they are organized into **rule groups** based on categories such as authentication bypass, injection flaws, insecure endpoints, and so forth. This grouping mechanism enables the engine to apply rules in a hierarchical manner, prioritizing those that are most relevant to the current target system. For instance, if the target is a mobile API with OAuth 2.0 authentication, the rule engine may prioritize rules related to token leakage or improper scope handling. This categorization also facilitates **rule pre-processing**, where the engine can pre-emptively filter out irrelevant rules based on the target's configuration, reducing the computational overhead during runtime.

The next layer in the architecture is the **context extraction and dynamic evaluation** phase. Here, the rule engine leverages the information extracted from the authenticated crawl to dynamically evaluate which rules are applicable to the current request-response pair. This involves extracting metadata such as HTTP methods, headers, cookies, query parameters, and response content, which are then compared against the conditions defined in the rules. For example, if a rule specifies that a vulnerability is triggered when a POST request is sent to an endpoint with a specific query parameter, the engine will check whether the current request meets these criteria. This dynamic evaluation ensures that only relevant rules are applied, reducing false positives and improving the accuracy of the scan.

A key component of this phase is the **context-aware rule filtering** mechanism. The engine uses a combination of static and dynamic context to filter out rules that are not applicable to the current target. Static context includes information such as the target's domain, protocol, and known authentication mechanisms, while dynamic context is derived from the live crawl data, such as the actual HTTP responses received during the scan. This dual-context approach allows the engine to adapt to both static configurations and runtime behaviors, ensuring that rules are evaluated in the most relevant context possible.

To further optimize performance, the rule engine employs **pattern matching optimizations** based on the nature of the rules. For example, rules that involve regular expressions or XPath queries are compiled into optimized patterns using tools such as PCRE (Perl Compatible Regular Expressions) or XPath evaluators. These compiled patterns are then matched against the extracted data in a highly efficient manner, minimizing the time required for each evaluation. Additionally, the engine may employ **memoization** techniques to cache results of previously evaluated rules, reducing redundant computations and improving scalability.

Another critical aspect of the rule matching architecture is the **rule application order and prioritization**. The engine ensures that rules are applied in a specific order, typically based on their severity or likelihood of triggering a false positive. For instance, high-severity rules may be applied first to ensure that the most critical vulnerabilities are identified early in the scan. This prioritization also allows for **rule overriding**, where a more specific rule can override a general one if it applies to the same condition. This mechanism is particularly useful in scenarios where multiple rules could potentially match the same request-response pair, ensuring that the most accurate and relevant rule is applied.

The architecture also incorporates **deduplication mechanisms** to handle potential overlaps in rule application. When multiple rules trigger for the same request, the engine evaluates their conditions and applies a deduplication policy based on predefined criteria such as rule specificity, confidence level, or impact score. This ensures that the final results are both accurate and concise, avoiding unnecessary duplication of findings.

Finally, the rule matching architecture integrates with the **SARIF output generation** pipeline to ensure that all matched rules are properly formatted and emitted in a standardized manner. The engine maps each matched rule to a corresponding SARIF result, including details such as the rule ID, severity, message, and location information. This integration allows for seamless compatibility with existing static analysis tools and ensures that dastlite's findings are easily consumable by developers and security teams.

In summary, the rule matching architecture of dastlite's rule engine is a sophisticated system that combines deterministic pattern matching, dynamic context evaluation, and efficient optimization techniques to ensure accurate and scalable application of active-scan rules. By leveraging structured rule definitions, hierarchical categorization, and context-aware filtering, the engine ensures that only relevant rules are applied to each request, minimizing false positives while maximizing the detection of potential vulnerabilities. This architecture forms the foundation for dastlite's ability to deliver precise and actionable security findings in a headless, config-as-code environment.

### Rule Prioritization and Conflict Resolution

Rule prioritization and conflict resolution are critical components of the dastlite rule engine, ensuring that the output SARIF file contains actionable, high-quality findings while minimizing false positives and redundant alerts. At its core, this mechanism involves a multi-tiered approach to evaluate and rank active scan rules based on their relevance, precision, and impact. The dastlite system employs a combination of static metadata, dynamic runtime data, and user-defined configurations to determine the priority of each rule during execution. This process is further refined through conflict resolution strategies that address overlapping or contradictory findings from different rules.

The prioritization mechanism begins with the classification of rules into predefined categories based on their type, severity, and scope. For example, rules that detect high-severity vulnerabilities such as SQL injection or cross-site scripting (XSS) are typically assigned higher priority than those that identify lower-risk issues like insecure HTTP methods. This classification is informed by the Open Web Application Security Project (OWASP) Top Ten and other industry-standard vulnerability frameworks, ensuring alignment with widely accepted security benchmarks. Each rule is tagged with metadata such as `severity`, `confidence`, and `impact`, which are used as initial criteria for prioritization. These tags are derived from the rule's definition and may be further refined during runtime based on contextual factors.

Dynamic runtime data plays a crucial role in refining rule priorities. During the crawling and scanning phase, dastlite collects contextual information such as the URL structure, HTTP response codes, headers, and payload content. This data is used to evaluate the relevance of each rule in real time. For instance, if a rule is designed to detect SQL injection vulnerabilities, its priority may be increased if the target endpoint receives POST requests with user-submitted data. Conversely, if the endpoint consistently returns 404 responses, the rule's priority may be reduced or temporarily disabled to avoid unnecessary alerts. This dynamic adjustment ensures that the rule engine remains adaptive to the specific characteristics of the target application under test.

User-defined configurations further enhance the prioritization process by allowing administrators to fine-tune the behavior of individual rules. These configurations can include parameters such as `max_priority`, `threshold`, and `weight`, which are used to adjust a rule's position in the priority hierarchy. For example, a rule that detects insecure direct object references (IDOR) might be assigned a lower default priority, but an administrator could increase its weight if the application handles sensitive data through URL parameters. This flexibility ensures that the rule engine can be tailored to the specific needs of an organization or project.

Conflict resolution is another essential aspect of the dastlite rule engine, addressing situations where multiple rules generate overlapping or conflicting findings for the same resource. This can occur when different rules detect similar issues on the same endpoint, leading to redundant or contradictory alerts. To resolve these conflicts, the system employs a combination of deterministic and probabilistic strategies based on the nature of the rules and their metadata.

Deterministic conflict resolution is applied when two or more rules produce findings that are explicitly contradictory. For example, if one rule identifies an endpoint as vulnerable to XSS and another rule flags the same endpoint as having a secure HTTP header, the system may resolve the conflict by evaluating which rule has higher priority based on its severity and confidence scores. In such cases, the higher-priority rule's finding is retained, while the lower-priority rule's result is either suppressed or marked as a potential false positive. This approach ensures that the SARIF output contains only the most relevant and accurate findings.

Probabilistic conflict resolution is used when rules generate overlapping but not necessarily contradictory findings. For example, if two rules detect different types of vulnerabilities on the same endpoint—such as one identifying an insecure cookie and another detecting a missing CSP header—the system may evaluate the likelihood that both findings are valid based on contextual data such as HTTP headers, response content, and user input. In such cases, the system may apply a weighted scoring model to determine which finding is more likely to be accurate. This model takes into account factors such as the rule's historical performance, the confidence level of its detection, and the specific characteristics of the target endpoint.

To further refine conflict resolution, dastlite incorporates a rule dependency graph that maps relationships between rules based on their context and overlap. This graph is used to identify potential conflicts and apply resolution strategies that minimize redundancy while preserving the integrity of findings. For example, if one rule is known to frequently generate false positives in certain environments, its priority may be adjusted relative to other rules that are more reliable in those contexts. This dependency-based approach ensures that the rule engine remains efficient and accurate across a wide range of applications.

The conflict resolution process also includes mechanisms for handling ambiguous or uncertain findings. In cases where multiple rules produce conflicting results, the system may apply a voting mechanism to determine the most likely outcome. For instance, if three rules detect a vulnerability on the same endpoint but with varying confidence levels, the system may aggregate their scores and select the finding with the highest combined score as the final result. This approach ensures that the SARIF output reflects the most probable and actionable findings while minimizing noise from less reliable rules.

Finally, the dastlite rule engine provides users with tools to manually review and adjust conflict resolution outcomes. These tools include a visual interface for inspecting conflicting findings, a comparison view for evaluating the pros and cons of each rule's detection, and an export feature for exporting resolved findings in a structured format. This allows administrators to fine-tune the behavior of the rule engine based on their specific requirements and ensure that the final SARIF file contains only the most relevant and accurate vulnerabilities. By combining deterministic and probabilistic strategies with user feedback, dastlite ensures that its rule engine remains both efficient and effective in delivering high-quality security findings.

To further enhance performance profiling, the system incorporates statistical analysis techniques that help identify trends and anomalies in rule execution. Additionally, statistical analysis can reveal patterns in how different types of rules perform under varying conditions, such as different payloads or response sizes. The profiling process also benefits from the use of real-time monitoring tools that provide immediate feedback on rule execution performance. These tools can be integrated into the DAST runner's architecture to continuously monitor key metrics such as CPU usage, memory consumption, and execution time. For example, if a rule is found to consume an excessive amount of CPU during execution, the system can dynamically adjust its priority or even temporarily disable it if its impact on performance is too significant. This real-time feedback loop allows for proactive optimization, ensuring that the DAST runner remains efficient even as new rules are added or existing ones are modified.

In addition to these technical mechanisms, the performance profiling of rule execution also involves the use of benchmarking frameworks that allow for comparative analysis of different rule implementations. The profiling data collected during these processes is then used to inform optimization strategies. Similarly, if a rule's execution time is consistently high, the system may investigate whether the rule can be simplified or refactored to reduce its complexity. Finally, performance profiling is an ongoing process that evolves as the DAST runner's ruleset grows and changes. This contextual filtering is implemented through a rule prioritization logic that evaluates the current context against predefined conditions. ### Deduplication Strategies in Rule Output

Deduplication is a critical component of any active scanning engine, particularly in the context of dastlite where the output must be both accurate and actionable. The primary goal of deduplication is to eliminate redundant or overlapping findings from the scan results, ensuring that each issue is reported only once and with sufficient context to be useful for remediation. This is especially important in environments where multiple rules may trigger similar alerts across different parts of the application. A well-designed deduplication strategy not only reduces noise but also improves the efficiency of the scanning process by minimizing redundant checks and false positives.

At the core of dastlite’s deduplication mechanism lies a combination of rule-based filtering and dynamic analysis of the scan results. Each rule in the active-scan ruleset is configured with metadata that includes a unique identifier, a description, and a set of conditions under which the rule should be applied. When a rule fires, it generates a finding that includes details such as the URL, HTTP method, request headers, response body, and a severity level. These findings are then passed to the deduplication module for processing.

The deduplication process begins by grouping findings based on their type and the specific rule that triggered them.
