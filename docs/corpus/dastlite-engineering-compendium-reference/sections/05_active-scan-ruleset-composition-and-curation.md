## 5. Active-Scan Ruleset Composition and Curation

### Rule Abstraction and Pattern Matching

Rule abstraction and pattern matching are foundational to the design and implementation of an active-scan ruleset in dastlite. These mechanisms enable the system to interpret and apply a diverse set of rules across a complex, authenticated web/mobile-API surface. Rule abstraction involves the process of generalizing specific vulnerabilities into structured, reusable patterns that can be applied dynamically during scanning. Pattern matching, conversely, is the technique by which these abstracted rules are matched against observed HTTP traffic to identify potential security issues. Together, they form the backbone of dastlite’s active-scan engine, allowing for both precision and scalability in vulnerability detection.

At the core of rule abstraction lies the concept of rule templates—structured representations of vulnerabilities that encapsulate both the expected behavior of a web application and the conditions under which a vulnerability might manifest. Each rule template is defined using a combination of HTTP method types (GET, POST, etc.), request headers, query parameters, body content, and response characteristics. For example, a rule template for detecting SQL injection might specify that a POST request with a query parameter containing a string like `"1' OR '1'='1"` should be matched against a response that includes an error message or a database-specific identifier such as `"MySQL"`. This abstraction allows the ruleset to remain flexible, as it does not require hardcoding specific payloads or endpoints but instead relies on patterns that can be applied across different applications and environments.

The abstraction process is further enhanced through the use of regular expressions and structured query language (SQL) pattern matching. Regular expressions are employed to identify common patterns in HTTP payloads, such as the presence of SQL keywords (`SELECT`, `UNION`, `WHERE`) or injection vectors like single quotes (`'`). These expressions are compiled into efficient pattern-matching engines that can quickly scan through large volumes of HTTP traffic without significant performance overhead. In addition, SQL pattern matching is used to detect anomalies in database queries, such as the presence of unescaped special characters or the use of dynamic SQL constructs. This dual-layer approach ensures that even subtle variations in injection patterns are captured, reducing the likelihood of false negatives.

Pattern matching in dastlite operates on a layered architecture that separates the rule abstraction logic from the actual traffic analysis. The first layer involves the parsing of HTTP requests and responses into structured data formats such as JSON or XML, which are then analyzed against the abstracted rule templates. This parsing process is critical for ensuring that all relevant components of an HTTP exchange—headers, query parameters, request bodies, and response content—are evaluated for potential matches. For instance, a rule template designed to detect cross-site scripting (XSS) vulnerabilities might require the system to check for the presence of `<script>` tags in the response body or the inclusion of user input in JavaScript contexts without proper escaping.

The second layer of pattern matching involves the application of the abstracted rules to the parsed HTTP data. This is achieved through a combination of deterministic and probabilistic matching strategies. Deterministic matching is used when the rule template specifies exact conditions that must be met, such as the presence of a specific HTTP status code or a particular header value. Probabilistic matching, on the other hand, is employed for rules that are more context-dependent, such as those designed to detect session fixation or insecure direct object references (IDOR). In these cases, the system may use statistical analysis or machine learning models to assess the likelihood of a vulnerability based on historical data and behavioral patterns.

To further enhance the accuracy of pattern matching, dastlite incorporates a dynamic scoring mechanism that assigns weights to different aspects of a rule template. For example, a rule that detects SQL injection might be weighted more heavily if it matches a response containing a database-specific error message, while a match against a generic error message might receive a lower score. This scoring system allows the system to prioritize high-confidence vulnerabilities while still capturing potential issues that may require further investigation.

The integration of rule abstraction and pattern matching is also supported by a modular architecture that allows for the dynamic loading and unloading of rule templates based on the specific needs of a scan. This modularity is particularly useful in scenarios where the web/mobile-API surface is large or heterogeneous, as it enables the system to apply only the relevant rules to specific parts of the application. For example, a mobile API might require a different set of rules for authentication tokens than a traditional web application, and dastlite can dynamically adjust its active-scan ruleset accordingly.

Moreover, the abstraction and pattern matching capabilities of dastlite are enhanced through the use of contextual metadata that is collected during the crawling process. This metadata includes information such as the URL structure, HTTP status codes, and response headers, which can be used to refine the matching process. For instance, a rule template designed to detect insecure HTTP methods might be applied only to endpoints that are accessible via GET or POST requests, based on the observed behavior of the application. This contextual awareness ensures that rules are applied in a targeted manner, reducing the risk of false positives and improving overall efficiency.

The effectiveness of rule abstraction and pattern matching is further validated through rigorous testing and validation mechanisms. Each rule template is subjected to a series of test cases that simulate different scenarios, such as varying payloads, response structures, and network conditions. These tests help identify edge cases and ensure that the ruleset remains robust even in complex environments. Additionally, dastlite employs continuous feedback loops where detected vulnerabilities are analyzed for their accuracy and relevance, allowing for iterative improvements to the rule templates over time.

In summary, the combination of rule abstraction and pattern matching in dastlite enables a highly flexible and scalable approach to active-scan vulnerability detection. By generalizing specific vulnerabilities into structured patterns and applying these patterns dynamically to HTTP traffic, the system achieves both precision and efficiency in identifying potential security issues. This dual-layered approach not only enhances the accuracy of the active-scan ruleset but also ensures that it remains adaptable to the evolving landscape of web and mobile APIs. Through the use of regular expressions, structured query language, dynamic scoring, and contextual metadata, dastlite provides a robust foundation for detecting vulnerabilities in authenticated environments while minimizing false positives and maximizing performance.

### Rule Prioritization and Weighting

The foundation of an effective active-scan ruleset lies not only in its breadth but also in its precision—specifically, in how it prioritizes and weights individual rules to align with operational goals, risk profiles, and technical constraints. Rule prioritization and weighting are critical mechanisms that determine which vulnerabilities are detected first, how they are ranked for remediation efforts, and how they contribute to overall security posture. These processes are not arbitrary; they are grounded in a combination of static analysis, dynamic behavioral modeling, and empirical data from past scan results. By systematically assigning weights to rules based on predefined criteria, the dastlite system ensures that its active-scan process remains both efficient and effective.

The prioritization of rules is often guided by the principle of **risk-based scanning**, which aligns with the broader goals of secure software development lifecycle (SDLC) integration. In this model, rules are evaluated based on their potential impact on the system, the likelihood of exploitation, and the ease with which they can be mitigated. For instance, a rule that identifies SQL injection vulnerabilities in a high-traffic API endpoint would typically be assigned a higher priority than one that detects a less critical issue such as a missing HTTP header. This approach ensures that the most impactful vulnerabilities are addressed first, optimizing resource allocation and reducing time-to-remediation.

Weighting rules is further refined through **dynamic scoring models**, which incorporate real-time data from ongoing scans and historical performance metrics. These models may use machine learning algorithms or rule-based heuristics to adjust the weight of a given rule based on its historical false-positive rate, detection accuracy, and the context in which it is applied. For example, a rule that flags insecure HTTP headers might be weighted differently when applied to a mobile API endpoint compared to a web application with a more robust security configuration. This contextual weighting allows the system to adapt to evolving threat landscapes and application architectures.

A concrete example of this process in action is the **dastlite rule engine's use of dynamic scoring**, which leverages a combination of static and runtime data to refine rule weights. During an initial scan, the system collects metadata about each rule, such as its detection frequency, false-positive rate, and the severity classification assigned by the rule author. These metrics are then fed into a **weighted scoring algorithm** that adjusts the rule's priority dynamically based on current scan conditions. For instance, if a particular rule has a high false-positive rate in a specific environment, its weight is reduced to minimize noise in the output. Conversely, if a rule consistently detects high-severity vulnerabilities in a given context, its weight is increased to ensure it remains prominent in the results.

The **rule prioritization framework** also incorporates **contextual metadata** such as the type of application under test (e.g., web, mobile API), the authentication method used, and the presence of specific technologies or frameworks. This metadata allows the system to tailor rule weights to the unique characteristics of each target environment. For example, a rule that detects insecure direct object references (IDOR) might be weighted higher in a mobile API context where data access patterns are more dynamic compared to a traditional web application. Similarly, rules related to session management or cross-site scripting (XSS) may be adjusted based on the presence of specific frameworks such as React or Angular, which have different security implications.

To illustrate this further, consider the **dastlite rule engine's implementation of contextual weighting** in its active-scan ruleset. The system maintains a **rule metadata repository** that stores information about each rule, including its technical scope, detection method, and historical performance data. When a scan is initiated, the system queries this repository to determine the appropriate weight for each rule based on the target environment's characteristics. For example, a rule that detects insecure cookie attributes might be weighted higher in an environment where cookies are used extensively for session management compared to one where tokens are used instead. This contextual weighting ensures that the ruleset remains both relevant and effective across diverse application landscapes.

The **rule prioritization framework** also supports **user-defined scoring parameters**, allowing teams to customize the weight of individual rules based on their specific security requirements. These parameters can be defined at the organizational level, team level, or even per scan configuration. For instance, a financial services organization might assign higher weights to rules that detect SQL injection or command injection vulnerabilities due to their potential for financial loss, while a healthcare provider might prioritize rules related to data privacy and access control. This flexibility ensures that the active-scan process aligns with the unique risk profiles of different domains.

In addition to static and user-defined parameters, the **rule prioritization framework** also incorporates **dynamic feedback loops**, where rule weights are continuously refined based on scan results and remediation outcomes. After a scan is completed, the system analyzes the detected vulnerabilities to assess their actual impact and whether they were false positives. This data is then used to adjust the weights of the corresponding rules for future scans. For example, if a particular rule consistently generates false positives in a specific environment, its weight is reduced to minimize unnecessary alerts. Conversely, if a rule detects a high-severity vulnerability that was previously overlooked, its weight is increased to ensure it remains prominent in the results.

The **rule prioritization framework** also integrates with **security policy engines**, allowing for real-time alignment of scan results with organizational security policies. These policies define acceptable risk thresholds, remediation timelines, and compliance requirements, which are used to further refine rule weights. For instance, a policy that mandates all high-severity vulnerabilities be addressed within 30 days would automatically increase the weight of rules that detect such vulnerabilities, ensuring they are prioritized in the scan results. This integration ensures that the active-scan process remains aligned with the organization's security objectives and compliance requirements.

The **rule prioritization framework** also supports **multi-criteria scoring**, where rules are evaluated based on multiple factors such as impact, exploitability, and remediation effort. For example, a rule that detects a high-impact vulnerability with a low remediation effort might be assigned a higher priority than one that detects a moderate-impact vulnerability requiring significant changes. This multi-criteria approach ensures that the active-scan process not only identifies vulnerabilities but also provides actionable insights for remediation.

In summary, the **rule prioritization and weighting** mechanisms in dastlite are designed to ensure that the active-scan ruleset remains both effective and efficient. By combining static and dynamic scoring models, contextual metadata, user-defined parameters, and real-time feedback loops, the system ensures that the most critical vulnerabilities are detected first, while minimizing false positives and aligning with organizational security goals. This approach not only enhances the accuracy of the scan results but also supports a more strategic and data-driven approach to vulnerability management.

### Rule Contextualization and Environment Binding

The process of rule contextualization and environment binding in dastlite’s active-scan ruleset composition is fundamentally about aligning scanning rules with the specific runtime environments they are intended to operate within. This alignment ensures that rules are not only syntactically valid but also semantically relevant to the target system, thereby improving both the accuracy and efficiency of the scan. Rule contextualization involves mapping each rule to a set of predefined environmental attributes—such as authentication mechanisms, API versions, or network configurations—that define the operational context in which the rule is applicable. Environment binding then formalizes this relationship by embedding these contextual parameters into the rule definition, enabling dastlite’s engine to dynamically select and execute rules based on the current state of the target system.

This approach is critical for mitigating false positives and false negatives that often arise when generic rules are applied to diverse environments. For instance, a rule designed to detect insecure HTTP headers may produce false positives if applied to an API that exclusively uses HTTPS, whereas the same rule could be contextually relevant in an environment where mixed content is still prevalent. By binding rules to their specific environmental contexts, dastlite ensures that each rule is executed only when its conditions are met by the current target configuration. This dynamic selection mechanism is implemented through a combination of metadata annotations and runtime introspection, allowing the engine to evaluate the relevance of a rule in real time.

One of the primary mechanisms for rule contextualization is the use of **environmental tags**—metadata fields embedded within each rule definition that specify the conditions under which the rule should be executed. These tags can include attributes such as `auth-type`, `api-version`, `protocol`, and `endpoint-pattern`. For example, a rule designed to detect misconfigured session cookies might be tagged with `auth-type: "bearer"` and `protocol: "https"`, ensuring that it is only applied to endpoints using bearer tokens over HTTPS. This level of granularity allows dastlite to apply rules selectively, reducing unnecessary scan overhead and improving the precision of vulnerability detection.

The binding of rules to their environmental contexts is further enhanced through **rule parameterization**, a mechanism that enables rules to accept dynamic inputs based on the target environment. For instance, a rule designed to test for SQL injection might include a parameter `query-pattern` that matches the specific SQL syntax used by the target database. This parameter can be dynamically resolved at runtime using dastlite’s configuration resolver, which evaluates the current environment state and injects appropriate values into the rule parameters. This approach not only increases the adaptability of rules but also ensures that they remain effective across different versions of the same API or application.

Another key aspect of rule contextualization is the integration of **environmental introspection** into the scanning process. dastlite’s engine is capable of introspecting the target system at runtime to gather detailed information about its configuration, such as authentication methods, supported protocols, and endpoint structures. This introspection is performed using a combination of automated discovery techniques, including HTTP method testing, cookie inspection, and header analysis. The gathered environmental data is then used to dynamically select and configure rules, ensuring that each rule is applied only when its conditions are met by the current target environment.

This dynamic selection process is implemented through a **rule evaluation pipeline** that processes each rule against a set of pre-defined environmental constraints. For example, if a rule is tagged with `auth-type: "basic"` and `endpoint-pattern: "/api/v1/users"`, the engine will first check whether the current target supports basic authentication and whether the request is directed to an endpoint matching the specified pattern. If both conditions are satisfied, the rule is executed; otherwise, it is skipped. This pipeline ensures that rules are only applied when they are relevant, thereby minimizing unnecessary network activity and reducing the risk of false positives.

The binding of rules to their environmental contexts also extends to **multi-environment support**, allowing dastlite to handle complex systems with multiple components or services operating under different configurations. For instance, a web application may expose both an API endpoint using OAuth2 and a legacy endpoint using basic authentication. In such cases, dastlite can apply different rule sets based on the authentication method used by each endpoint, ensuring that rules are executed in the most appropriate context. This capability is achieved through **environment-specific rule groups**, which are predefined collections of rules that are tailored to specific environmental configurations. These groups can be dynamically loaded based on the introspection results, allowing dastlite to adapt its scanning strategy to the unique characteristics of each target system.

A concrete example of rule contextualization and environment binding in action is the detection of insecure cookie attributes. A generic rule might look for cookies without the `Secure` attribute, but this could result in false positives if applied to an API that uses HTTPS exclusively. To address this, dastlite’s ruleset includes a contextually bound variant of this rule that is tagged with `protocol: "https"` and `auth-type: "bearer"`. When the engine introspects the target system and confirms that it uses HTTPS and bearer tokens, it applies this rule to detect cookies that lack the `Secure` attribute. This contextual approach ensures that the rule is only executed in environments where it is relevant, thereby improving both accuracy and performance.

Another illustrative example involves the detection of misconfigured CORS policies. A rule designed to identify insecure CORS headers might be tagged with `endpoint-pattern: "/api/*"` and `auth-type: "oauth2"`, ensuring that it is applied only to endpoints that use OAuth2 for authentication. During the scan, dastlite’s engine evaluates the current request context and applies this rule only when the endpoint matches the specified pattern and the authentication method is OAuth2. This ensures that the rule is executed in the most relevant context, reducing the risk of false positives and improving the overall effectiveness of the scan.

The implementation of rule contextualization and environment binding in dastlite is supported by a robust framework of **metadata-driven configuration**, which allows rules to be dynamically adapted based on environmental conditions. This framework includes a set of predefined environmental attributes that can be used to tag and categorize rules, as well as a runtime resolver that evaluates these attributes against the current target state. The resolver uses a combination of static metadata and dynamic introspection to determine the appropriate rule execution context, ensuring that each rule is applied only when its conditions are met.

In addition to improving accuracy and performance, rule contextualization and environment binding also enhance the **maintainability** of the ruleset. By explicitly defining the environmental conditions under which a rule should be applied, developers can more easily understand the scope and limitations of each rule. This makes it simpler to update or modify rules as the target system evolves, ensuring that the ruleset remains aligned with the current environment. Furthermore, this approach facilitates **rule reuse**, as contextually bound rules can be applied to different systems with similar environmental configurations, reducing the need for redundant rule definitions.

Overall, the process of rule contextualization and environment binding in dastlite’s active-scan ruleset composition is a critical component of its ability to deliver accurate, efficient, and adaptable security testing. By aligning rules with their specific environmental contexts, dastlite ensures that each rule is executed only when it is relevant, thereby improving the precision of vulnerability detection and reducing unnecessary scan overhead. This approach not only enhances the effectiveness of the scanning process but also supports the long-term maintainability and adaptability of the ruleset, making it a cornerstone of dastlite’s architecture.

### Rule Conflict Resolution and Deduplication

Rule conflict resolution and deduplication in the active-scan ruleset are critical components of ensuring accurate and actionable results from the dastlite engine. These processes address inherent ambiguities in rule definitions, overlapping conditions, and redundant alerts, thereby improving the precision and utility of the scan output. At their core, these mechanisms rely on structured logic, metadata-driven prioritization, and a robust framework for reconciling conflicting or overlapping rule outcomes.

The first step in resolving rule conflicts is identifying potential overlaps between rules. This is achieved through a systematic analysis of rule conditions, actions, and their applicability to a given target surface. For instance, two rules may both trigger on the same HTTP status code (e.g., 403 Forbidden) but differ in their payloads or response bodies. In such cases, the dastlite engine employs a conflict detection algorithm that evaluates the similarity of conditions and the specificity of rule actions. If two rules are determined to be redundant or overlapping, the system may prioritize one based on predefined criteria such as rule age, author authority, or impact severity.

One concrete example of conflict resolution in action is the handling of authentication-related rules. Suppose two rules are defined: one for detecting potential session fixation vulnerabilities and another for identifying weak password policies. If both rules apply to the same login endpoint and produce conflicting alerts, the dastlite engine evaluates their conditions and actions. The system may resolve the conflict by applying a priority-based resolution strategy, where higher-priority rules take precedence. This prioritization is often based on metadata such as rule category, threat model alignment, or user-defined weights assigned to specific rules.

Deduplication mechanisms further enhance the precision of scan results by eliminating redundant alerts that arise from overlapping conditions or identical payloads. The dastlite engine employs a combination of static and dynamic deduplication strategies. Static deduplication involves comparing rule definitions to identify duplicates based on fixed attributes such as HTTP method, URL pattern, and payload structure. Dynamic deduplication, on the other hand, leverages runtime data from the scan to group alerts that share similar characteristics, such as identical response bodies or matching HTTP headers.

A key component of dynamic deduplication is the use of a signature-based matching system. The dastlite engine generates unique signatures for each alert based on a combination of factors, including the HTTP method, URL path, response body, and any specific payload data. These signatures are then compared against a deduplication database to identify and merge alerts that are deemed duplicates. For example, if two different rules trigger on the same endpoint and produce identical response bodies, the system may consolidate these into a single alert, reducing noise in the final output.

The deduplication process is also enhanced by the use of contextual metadata. The dastlite engine tracks additional information such as the timestamp of the alert, the scan session ID, and the specific rule that triggered it. This metadata allows the system to distinguish between alerts that are genuinely unique and those that may appear similar but stem from different sources or contexts. For instance, if two identical alerts are generated by different rules during the same scan session, the system can flag them as potential duplicates and apply a threshold-based merging strategy to consolidate them.

The resolution of rule conflicts and deduplication is further supported by the use of a rule dependency graph. This graph maps out the relationships between rules, including dependencies, overlaps, and potential conflicts. By analyzing this graph, the dastlite engine can identify chains of rule execution that may lead to redundant or conflicting alerts. For example, if Rule A triggers an alert that then activates Rule B, the system can evaluate whether the combination of these rules leads to unnecessary duplication. This approach allows for a more holistic view of the ruleset and enables the engine to optimize the execution order and outcomes.

In addition to static and dynamic deduplication, the dastlite engine employs a rule-specific deduplication mechanism that leverages metadata such as rule version, author, and configuration parameters. This allows for fine-grained control over which rules are prioritized or excluded during deduplication. For instance, if two rules are defined by different authors but produce identical alerts, the system may apply a rule-specific deduplication policy based on the author's reputation or the rule's historical performance.

The dastlite engine also incorporates a feedback loop mechanism for continuous improvement of conflict resolution and deduplication. This mechanism allows users to manually review and adjust the prioritization of rules or the deduplication thresholds based on their specific use cases. For example, if a particular rule is frequently flagged as conflicting with others, the user can adjust its priority or modify its conditions to better align with the overall ruleset. This feedback loop ensures that the system adapts to evolving requirements and improves over time.

In practice, the implementation of these mechanisms requires careful consideration of performance and scalability. The dastlite engine must efficiently process large volumes of scan data while maintaining the accuracy of conflict resolution and deduplication. This is achieved through a combination of optimized algorithms, efficient data structures, and parallel processing capabilities. For instance, the system may use bloom filters or hash tables to quickly identify potential duplicates without scanning the entire dataset.

The effectiveness of these mechanisms is further validated by real-world examples. In one case study, a financial institution used dastlite to scan its internal API endpoints for vulnerabilities. During the scan, multiple rules were triggered on the same endpoint, leading to conflicting alerts. By applying the conflict resolution and deduplication mechanisms described above, the system was able to consolidate redundant alerts and prioritize those with higher impact. This resulted in a significant reduction in false positives and improved the overall quality of the scan output.

Another example involves a healthcare provider that used dastlite to identify potential security issues in its mobile application. During the scan, several rules were triggered on the same endpoint, leading to overlapping alerts. The system's conflict resolution mechanisms helped to resolve these conflicts by prioritizing rules based on their relevance to the application's threat model. This allowed the team to focus on the most critical vulnerabilities while minimizing noise from less relevant alerts.

In conclusion, rule conflict resolution and deduplication are essential components of the active-scan ruleset composition and curation in dastlite. These mechanisms ensure that the scan output is accurate, actionable, and free from redundant or conflicting alerts. By leveraging structured logic, metadata-driven prioritization, and a robust framework for reconciling conflicts, the dastlite engine delivers high-quality results that meet the needs of modern application security practices.

### Rule Maintenance and Versioning Strategy

The rule maintenance and versioning strategy for the dastlite active-scan ruleset is a structured, versioned, and modular approach that ensures the ruleset remains current, consistent, and maintainable over time. This strategy is grounded in the principles of configuration-as-code, where each rule is treated as a first-class entity with its own metadata, dependencies, and version history. The dastlite system employs a declarative model for rule definitions, allowing for precise control over when, how, and under what conditions a rule is applied during a scan. This model is complemented by a versioning mechanism that tracks changes to rules, enabling rollback, auditing, and seamless integration with CI/CD pipelines.

At the core of this strategy is the use of semantic versioning (SemVer) for each rule. Every rule in the dastlite ruleset is assigned a version number in the format `MAJOR.MINOR.PATCH`, where the major version indicates breaking changes, the minor version indicates new features or enhancements that are backward-compatible, and the patch version represents bug fixes or minor adjustments. This versioning scheme ensures that users can understand the impact of any rule update without requiring extensive documentation or manual intervention. For example, a rule with version `1.2.3` can be safely updated to `1.3.0` if it introduces new HTTP headers or payload patterns without altering the expected behavior of existing tests.

The dastlite ruleset is organized into a modular structure, where each rule is stored as a separate YAML file in a version-controlled repository. This modular approach allows for fine-grained control over individual rules, enabling teams to update, disable, or enable specific rules without affecting the rest of the ruleset. Each rule file contains metadata such as the rule name, description, severity level, and dependencies on other rules or external libraries. Additionally, each rule includes a `version` field that specifies its current SemVer, along with a `changelog` that documents changes made in each version. This metadata is used by the dastlite engine to load, validate, and apply rules during a scan.

The versioning strategy also supports branching and tagging in the repository, allowing for parallel development of different rule versions. For instance, a team might maintain a `main` branch for stable releases and a `develop` branch for ongoing development. When a new version of a rule is ready for release, it is tagged with a SemVer label, such as `v1.4.0`, and merged into the `main` branch. This process ensures that only tested and validated rules are included in the stable release, while development changes can be reviewed and integrated incrementally.

To further enhance maintainability, the dastlite system provides a rule dependency management mechanism. Each rule may specify dependencies on other rules or external libraries, which are resolved during the build process. This allows for modular updates, where changes to a dependent rule can be propagated automatically without requiring manual intervention. For example, if a new version of a common HTTP header validation rule is released, all rules that depend on it will automatically use the updated version during a scan. This dependency management ensures that the ruleset remains consistent and up-to-date across different environments and configurations.

The versioning strategy also includes a rollback mechanism, which allows users to revert to a previous version of a rule if an update introduces unintended side effects. This is achieved by maintaining a history of all rule versions in the repository, with each version tagged and accessible via Git. When a user wants to roll back a rule to a specific version, they can simply reference the corresponding tag or commit hash, and the dastlite engine will load that version during the scan. This rollback capability is particularly useful in production environments where stability is critical.

In addition to versioning rules, the dastlite system tracks changes to the ruleset as a whole.
