## 3. Config-as-Code Framework Design

### Configuration Grammar and Syntax Specification

The configuration grammar and syntax specification for dastlite are defined using a formalized structure built upon the principles of declarative programming and structured data representation. At its core, the configuration is expressed in a domain-specific language (DSL) tailored for defining web and API surfaces, authentication mechanisms, scan rulesets, and output formats. This DSL is designed to be both human-readable and machine-parsable, ensuring that configurations can be version-controlled, audited, and dynamically generated or modified without introducing ambiguity or operational inconsistencies.

The grammar is built upon a hierarchical structure, with the top-level configuration object containing nested sections for defining the target surface, authentication strategy, ruleset, and output settings. The syntax is grounded in JSON-like semantics but augmented with custom types and operators that reflect the specific needs of dastlite's execution model. For example, the `targets` section is a collection of objects, each representing an endpoint or API resource, and is defined using a compound key-value structure that includes attributes such as `url`, `method`, and `headers`. This structure enables precise specification of the surface to be scanned, ensuring that the crawler operates within well-defined boundaries.

Authentication strategies are similarly expressed through a dedicated section, `authentication`, which may include sub-sections for defining credentials, session tokens, or OAuth2 flows. The syntax here leverages named entities and type annotations to distinguish between different authentication mechanisms. For instance, a basic HTTP authentication setup would be defined with a `type` field set to `"basic"` and include `username` and `password` fields. In contrast, an OAuth2 flow might use a `type` of `"oauth2"` with sub-fields such as `client_id`, `client_secret`, and `token_url`. These distinctions are critical for ensuring that the DAST runner correctly initializes and maintains authentication state during the scan.

The ruleset configuration is another pivotal component, structured to allow users to curate and apply a set of active-scan rules tailored to their environment. The `ruleset` section includes a list of rule identifiers, each corresponding to a specific vulnerability detection mechanism. These identifiers are mapped to predefined active-scan rules stored in dastlite's internal library, which may include rules for detecting SQL injection, XSS, CSRF, and other common vulnerabilities. The syntax allows for filtering and prioritization of rules through attributes such as `enabled`, `severity`, and `tags`. For example, a user might specify a subset of rules with severity levels `"high"` and `"medium"` by including a `filter` clause that references these attributes. This enables fine-grained control over the scan's coverage and performance.

The syntax also supports conditional expressions and logical operators to define dynamic configurations. For instance, authentication parameters can be conditionally applied based on the target URL or method. A rule might be enabled only if a certain header is present or if the response status code falls within a specific range. These conditions are expressed using inline expressions that are evaluated during configuration parsing. This feature enhances flexibility, allowing users to tailor configurations to complex environments without requiring extensive scripting or external tools.

To ensure consistency and clarity, the DSL incorporates a set of reserved keywords and operators that govern the structure and behavior of configurations. Keywords such as `target`, `auth`, `rule`, and `output` serve as anchors for different sections, while operators like `and`, `or`, and `not` enable logical combinations within rule conditions or configuration filters. Additionally, the grammar includes mechanisms for referencing other configuration elements, such as using `$ref` to point to nested sections or external configuration files. This referencing capability supports modular configurations, where complex setups can be broken down into smaller, reusable components.

The syntax also defines a strict schema for each section, ensuring that required fields are present and that optional fields are appropriately handled. For example, the `targets` section must include at least the `url` field, while optional fields such as `method`, `headers`, and `params` can be included to further refine the scan's behavior. Similarly, the `ruleset` section requires a list of rule identifiers, with optional filters to limit the scope of the scan. These schema definitions are enforced during configuration parsing, preventing runtime errors caused by missing or malformed data.

Another key aspect of the syntax is its support for metadata and annotations, which allow users to add contextual information to their configurations. Metadata fields such as `description`, `author`, and `version` provide insight into the purpose and origin of a configuration, while annotations can be used to specify additional behavior or constraints. For example, an annotation might indicate that a particular rule should only be applied during certain hours of the day or that a target should be crawled with a specific timeout value. These metadata and annotation mechanisms enhance the configurability and maintainability of dastlite's setups.

The DSL also includes a set of built-in functions and transformations that facilitate advanced configuration logic. For instance, users can leverage functions to dynamically generate URLs based on parameters, manipulate headers or payloads, or apply transformations to response data. These functions are defined in a standardized manner, with clear input and output specifications, ensuring that they can be reliably used across different configurations. An example might involve using a function to append a timestamp to a request header, enabling session-specific scanning without requiring manual intervention.

Finally, the syntax is designed to support versioning and evolution of configurations over time. This is achieved through the inclusion of a `version` field at the top level of the configuration, which specifies the format and schema version being used. When parsing a configuration, dastlite checks the version against its supported versions and applies any necessary compatibility transformations or deprecations. This ensures that configurations remain backward-compatible while allowing for the introduction of new features and syntax elements in future releases.

In summary, the configuration grammar and syntax specification for dastlite are designed to be both expressive and precise, enabling users to define complex scan environments with clarity and control. Through a structured DSL grounded in JSON-like semantics, dastlite provides a robust framework for configuring its DAST execution model, ensuring that configurations are consistent, maintainable, and adaptable to evolving security requirements. The combination of hierarchical organization, conditional logic, metadata support, and versioning mechanisms ensures that the configuration system is both powerful and user-friendly, laying the foundation for the rest of dastlite's architecture.

### Modular Rule and Policy Integration Architecture

The modular rule and policy integration architecture within the dastlite framework is a foundational element that enables the system to dynamically incorporate, manage, and execute a curated set of active scan rules. This architecture is built upon a layered design that separates the logic for rule execution from the configuration and policy management, allowing for high flexibility, scalability, and maintainability. At its core, this architecture leverages a plugin-based model, where each rule or policy is encapsulated as a self-contained module, enabling independent development, testing, and deployment. This modular approach ensures that changes to one rule or policy do not inadvertently affect others, thereby reducing the risk of cascading failures and simplifying system updates.

The integration of rules and policies is facilitated through a centralized configuration engine, which acts as a mediator between the rule modules and the execution engine. This engine dynamically loads, validates, and applies the appropriate rules based on the current context, such as the target application’s authentication state, API endpoints, or predefined security profiles. The configuration engine supports both declarative and imperative rule definitions, allowing for fine-grained control over when and how each rule is executed. For instance, a rule might be configured to run only during specific scan phases, or it may be triggered based on the presence of certain headers or payloads. This level of configurability ensures that the active scan ruleset can be tailored to meet the unique requirements of different applications and environments.

A key component of this architecture is the rule module interface, which defines a standardized API for interacting with the execution engine. Each rule module implements this interface, providing methods for initialization, execution, and result reporting. The interface abstracts the internal logic of each rule, allowing them to be interchangeable and reusable across different projects or environments. For example, a rule designed to detect SQL injection vulnerabilities can be used in both web and API contexts, provided it adheres to the interface specification. This abstraction not only simplifies the development process but also enhances the maintainability of the system by isolating changes to individual rules without affecting the broader architecture.

The policy integration layer further enhances the flexibility of the modular architecture by allowing for dynamic rule prioritization and conditional execution. Policies are defined as sets of rules that are applied in a specific order or under certain conditions, enabling the system to adapt its scanning behavior based on the target application’s characteristics. For instance, a policy might prioritize rules that detect authentication bypass vulnerabilities when scanning an API with OAuth2 authentication, while deactivating rules that are less relevant in such contexts. This conditional execution is managed through a policy engine that evaluates the current scan context and applies the appropriate ruleset. The policy engine supports both static and dynamic policies, where static policies are predefined and applied consistently across all scans, while dynamic policies are generated based on runtime data such as the application’s response times or authentication tokens.

The modular architecture also incorporates a rule dependency management system, which ensures that rules can be composed in a hierarchical manner. This system allows for the creation of composite rules that combine multiple individual rules to achieve more complex detection scenarios. For example, a composite rule might integrate a SQL injection detection rule with a rule that checks for weak password policies, providing a more holistic assessment of the application’s security posture. Dependency management is implemented through a directed acyclic graph (DAG) where each node represents a rule or policy, and edges represent dependencies between them. This DAG ensures that rules are executed in the correct order and that any changes to a dependent rule are propagated appropriately.

To support the dynamic nature of the modular architecture, the system employs a versioning mechanism for both rules and policies. Each rule module is assigned a version number, which allows the configuration engine to track changes and ensure compatibility with the execution environment. Versioning also facilitates rollback capabilities, enabling users to revert to a previous state if an update introduces unexpected behavior. Similarly, policies are versioned to maintain a history of their configurations, allowing for auditability and traceability. This versioning mechanism is integrated with the configuration engine, ensuring that rule and policy updates are applied seamlessly without disrupting ongoing scans.

The modular architecture also includes a metadata system that provides detailed information about each rule and policy, such as their purpose, dependencies, performance characteristics, and supported environments. This metadata is used by the configuration engine to optimize the execution of rules and policies, ensuring that they are applied efficiently. For example, the metadata might indicate that a particular rule is resource-intensive and should be executed only during off-peak hours, while another rule with minimal overhead can be applied more frequently. The metadata system is implemented as a JSON-based schema, which is accessible through a centralized repository, allowing for easy integration with external tools and systems.

In addition to the technical components, the modular architecture emphasizes extensibility and community-driven development. By decoupling rules and policies from the core framework, developers can contribute new rules or modify existing ones without requiring changes to the main system. This approach fosters a collaborative environment where third-party contributors can enhance the active scan capabilities of dastlite. For instance, a developer might create a rule for detecting API-specific vulnerabilities and submit it as a plugin, which can then be integrated into the framework through a simple configuration update. This extensibility is further supported by a package management system that allows users to install, update, and manage rules and policies from a central repository.

The integration of modular rules and policies is also enhanced by the use of declarative configuration files, which define how rules and policies should be applied within the framework. These configuration files are written in a structured format, such as YAML or JSON, and specify parameters such as rule priorities, execution conditions, and output formats. The configuration engine parses these files and applies the specified settings during scan execution, ensuring that the active scan ruleset is tailored to the specific needs of each project. This declarative approach simplifies the management of complex rule sets, as users can focus on defining the desired behavior rather than writing low-level code.

To ensure consistency and reliability, the modular architecture includes a validation mechanism that checks the integrity of rule and policy configurations before they are applied. This validation process verifies that all required parameters are present, dependencies are correctly resolved, and the configuration adheres to the defined schema. If any discrepancies are detected, the system provides detailed error messages, allowing users to quickly identify and correct issues. This validation is performed during the initialization phase of the scan, ensuring that only valid configurations are used for execution.

In summary, the modular rule and policy integration architecture of dastlite is a sophisticated design that enables the system to dynamically incorporate, manage, and execute a curated set of active scan rules. By leveraging a plugin-based model, standardized interfaces, and a centralized configuration engine, the architecture ensures flexibility, scalability, and maintainability. The inclusion of policy engines, dependency management systems, versioning mechanisms, and metadata enhances the adaptability of the framework, allowing it to evolve with the changing needs of applications and environments. Through this modular design, dastlite provides a robust and extensible solution for performing active scans on authenticated web and mobile-API surfaces, ensuring that security assessments are both comprehensive and efficient.

### Dynamic Credential Management and Injection

Dynamic Credential Management and Injection is a core component of the dastlite framework, ensuring secure and efficient handling of authentication credentials during web/mobile API surface crawling. The mechanism is designed to support both static and dynamic credential sources, enabling seamless integration with identity providers (IdPs) and internal authentication systems. This section explores the architecture, implementation strategies, and operational considerations for dynamically managing and injecting credentials into dastlite’s execution pipeline.

The primary objective of dynamic credential management is to provide a flexible, secure, and auditable means of handling authentication credentials across diverse environments. Traditional approaches often rely on hard-coded credentials stored in configuration files or environment variables, which pose risks such as exposure through logging or misconfiguration. By contrast, dastlite’s dynamic credential management system abstracts credential handling into a modular, pluggable architecture that supports multiple sources, including secrets managers, identity providers, and internal authentication services.

At the heart of this system is the Credential Manager component, which acts as a central hub for retrieving, validating, and injecting credentials into the crawling process. The Credential Manager is implemented as a service within the dastlite framework, with an interface defined in the config-as-code schema. This interface supports multiple credential sources, each represented by a plugin or adapter that implements a standardized API for credential retrieval. For example, the `secrets-manager` plugin integrates with AWS Secrets Manager, while the `oidc-provider` plugin enables integration with OpenID Connect (OIDC)-compliant identity providers such as Okta or Auth0.

The Credential Manager supports both static and dynamic credential sources. Static sources are used for fixed credentials that do not change over time, such as API keys or database passwords. These are typically retrieved from configuration files or environment variables and stored in a secure vault or secret store. Dynamic sources, on the other hand, are used for credentials that require periodic renewal or are tied to user sessions, such as OAuth2 access tokens or SAML assertions. The Credential Manager is designed to handle these use cases by abstracting the credential retrieval logic into reusable plugins, which can be configured via the config-as-code schema.

The injection of credentials into the crawling process is handled through a dedicated Credential Injector component. This component is responsible for applying retrieved credentials to the appropriate endpoints and services within the target application. The injection process is designed to be context-aware, meaning that it dynamically selects the appropriate credential based on the target endpoint’s authentication requirements. For example, if an endpoint requires Basic Authentication, the Credential Injector will apply the corresponding username and password from the retrieved credentials. If the endpoint uses OAuth2, the injector will apply the access token obtained from the Credential Manager.

To ensure security and prevent credential leakage, the Credential Injector employs several best practices. First, it ensures that credentials are only injected into the necessary parts of the crawling pipeline, minimizing the risk of exposure. Second, it supports secure credential transmission protocols such as TLS for communication with secret stores and identity providers. Third, it includes mechanisms for credential rotation and expiration, ensuring that outdated or compromised credentials are automatically replaced.

The dynamic nature of credential management is further enhanced by support for multi-factor authentication (MFA) and conditional access policies. For example, when accessing a sensitive endpoint, the Credential Manager can be configured to require MFA before retrieving the corresponding credentials. This adds an additional layer of security, ensuring that only authorized users or services can access sensitive data.

The integration of dynamic credential management with dastlite’s config-as-code framework is achieved through a combination of declarative configuration and runtime execution. The config-as-code schema defines the necessary parameters for credential sources, such as the type of secret store, the name of the secret, and the authentication method. These configurations are stored in version-controlled files, allowing for auditability and traceability. During runtime, the Credential Manager parses these configurations and dynamically retrieves the required credentials based on the target application’s requirements.

One of the key advantages of this approach is its extensibility. New credential sources can be added by implementing the standardized API provided by the Credential Manager. This allows developers to integrate with custom secret stores or proprietary identity systems without modifying the core framework. For example, a company using an internal authentication service can develop a custom plugin that interfaces with their system and integrates seamlessly into dastlite’s credential management pipeline.

The dynamic injection of credentials also supports advanced use cases such as session-based crawling and token-based authentication. In session-based crawling, the Credential Injector maintains a session context, ensuring that credentials are applied consistently across multiple requests. This is particularly useful for applications that require persistent sessions or cookies for authentication. In token-based authentication, the Credential Injector manages the lifecycle of access tokens, including renewal and expiration, to ensure continuous access to protected endpoints.

To further enhance security, the Credential Manager includes support for credential encryption and decryption. Sensitive credentials retrieved from secret stores are encrypted using industry-standard algorithms such as AES-256, and decrypted only when needed for injection. This ensures that credentials remain secure even if they are stored in plaintext within the config-as-code files.

The dynamic credential management system is also designed to handle credential rotation and expiration gracefully. When a credential reaches its expiration date or is rotated, the Credential Manager automatically retrieves the new credential from the source, ensuring continuous access without interruption. This is particularly important for services that require frequent credential updates, such as those using temporary tokens or short-lived access keys.

In addition to security and reliability, dynamic credential management supports operational efficiency by reducing the need for hard-coded credentials in configuration files. This simplifies maintenance and reduces the risk of credential exposure through logging or misconfiguration. The modular design of the Credential Manager also enables teams to manage credentials at scale, with different configurations for development, staging, and production environments.

The integration of dynamic credential management with dastlite’s active-scan ruleset ensures that authentication credentials are properly applied during security testing. For example, when a rule requires access to a protected endpoint, the Credential Injector automatically applies the appropriate credentials, allowing the scan to proceed without interruption. This seamless integration ensures that the security testing process is both accurate and efficient.

Finally, the dynamic credential management system includes robust auditing and logging capabilities. Every credential retrieval and injection operation is logged with timestamps, user identifiers, and contextual information, enabling teams to track the usage of credentials and detect potential security issues. These logs can be integrated with existing monitoring and alerting systems, providing visibility into credential activity across the organization.

In conclusion, the dynamic credential management and injection system in dastlite represents a significant advancement in secure and efficient authentication handling for web/mobile API surface crawling. By abstracting credential retrieval and injection into a modular, pluggable architecture, dastlite ensures flexibility, security, and operational efficiency. The integration with the config-as-code framework enables teams to manage credentials at scale, while the support for dynamic sources and advanced use cases such as MFA and session-based crawling enhances the system’s versatility. Through careful design and implementation, this system ensures that authentication credentials are handled securely, reliably, and seamlessly throughout the dastlite execution pipeline.

### Target Topology and Dependency Resolution

The target topology and dependency resolution in the dastlite framework are foundational to its ability to accurately model and traverse the authenticated web/mobile-API surface during active scans. At the core of this mechanism is a graph-based representation of the application's architecture, where nodes represent endpoints or components, and edges represent dependencies or interconnections between them. This topology is not static but dynamically constructed through dependency resolution, which identifies and resolves the relationships between components at runtime. The process begins with the ingestion of configuration data—typically in YAML or JSON format—where each component is defined with its attributes, such as URL paths, HTTP methods, authentication mechanisms, and interdependencies.

The graph-based representation is essential because it allows dastlite to model not only the individual endpoints but also their interactions. For instance, an API endpoint for user authentication may depend on a database endpoint for user validation, or a mobile app API may interact with a third-party service for payment processing. These dependencies are captured in the graph as directed edges, enabling the framework to traverse the topology in a structured manner. The resolution of these dependencies is not merely a matter of parsing configuration data but involves evaluating the runtime context of each component, including authentication state, session tokens, and any conditional logic that may affect endpoint behavior.

The dependency resolution process begins with the parsing of the configuration data, which is typically structured as a set of components, each with its own properties and relationships. For example, a component representing the user authentication endpoint might be defined with attributes such as `path: /api/auth/login`, `method: POST`, `authentication: OAuth2`, and `dependencies: [user-creation, session-management]`. These dependencies are then resolved by traversing the graph and ensuring that all required components are included in the scan. The resolution algorithm must account for both direct and indirect dependencies, such as when a component depends on another component that, in turn, depends on a third.

One of the key challenges in dependency resolution is handling conditional dependencies, where certain endpoints or components are only accessible under specific conditions. For example, an API endpoint might require a valid session token to be present in the request headers. In such cases, dastlite must dynamically determine whether the condition is met before including the component in the scan. This is achieved through a combination of static analysis of the configuration data and runtime evaluation of the authentication state. The framework uses a set of predefined rules and heuristics to infer the conditions under which a component can be accessed, ensuring that the dependency resolution process is both accurate and efficient.

Another important aspect of dependency resolution is the handling of circular dependencies, where two or more components depend on each other in a loop. This can lead to infinite loops during traversal if not properly managed. To address this, dastlite employs a topological sorting algorithm that ensures components are processed in an order that respects their dependencies. The algorithm starts by identifying all components with no incoming edges (i.e., those without dependencies), processes them, and then iteratively removes them from the graph while updating the dependencies of their dependents. This process continues until all components are processed or a cycle is detected. In the case of a cycle, dastlite uses a depth-first search approach to detect the loop and either resolves it by breaking the cycle or marks the components as part of a circular dependency for further analysis.

The configuration data also includes metadata that describes the relationships between components, such as `requires`, `depends_on`, and `optional_dependencies`. These metadata fields are parsed and used to construct the graph representation. For example, a component might have a `requires` field that specifies another component it depends on, or an `optional_dependency` that indicates a component that may be included but is not essential for the scan. The framework uses this metadata to build a directed acyclic graph (DAG) of dependencies, which is then used to traverse the topology in a controlled and systematic manner.

In addition to static configuration data, dastlite also incorporates dynamic information about the application's runtime behavior. This includes session tokens, cookies, headers, and any other contextual data that may affect the accessibility of endpoints. For instance, if a component requires a specific cookie to be present in the request, dastlite will ensure that the cookie is included in the request headers before attempting to access the endpoint. This dynamic information is integrated into the dependency resolution process, allowing the framework to accurately model the application's behavior and dependencies.

The resolution of dependencies is also influenced by the authentication strategy used by the application. For example, an OAuth2-based authentication system may require the framework to first obtain an access token before accessing certain endpoints. In such cases, dastlite uses a set of predefined rules to determine the order in which components should be processed. The framework first processes the authentication component to obtain the necessary credentials, and then proceeds to process the dependent components that require those credentials. This ensures that the dependency resolution process is both accurate and efficient, even in complex authentication scenarios.

Finally, the target topology and dependency resolution mechanisms are tightly integrated with the active-scan ruleset. The framework uses the resolved dependencies to determine which endpoints and components are eligible for scanning, ensuring that only relevant and accessible components are included in the scan. This integration allows dastlite to emit deduplicated SARIF files that accurately reflect the scanned surface, while also minimizing unnecessary scans of irrelevant or inaccessible components. By combining static configuration data with dynamic runtime information, dastlite ensures that the dependency resolution process is both comprehensive and precise, enabling the framework to effectively model the authenticated web/mobile-API surface during active scans.

### Output Formatting and SARIF Emission Pipeline

The output formatting and SARIF emission pipeline in dastlite are designed to ensure that scan results are both structured and consumable by a wide array of tools and platforms. At its core, the pipeline is responsible for transforming raw scan data—generated through the execution of active scan rules during the crawl phase—into a standardized format that adheres to the Static Analysis Results Interchange Format (SARIF). This transformation is not merely a technical convenience but a strategic choice rooted in the need for interoperability, auditability, and integration with existing DevOps toolchains. The SARIF specification, developed by the Open Source Security Foundation (OSS-Foundation), provides a flexible and extensible format that allows for rich metadata to be associated with each vulnerability, including severity, location, and remediation guidance. By emitting results in SARIF, dastlite ensures compatibility with tools such as Azure DevOps, GitHub Advanced Security, and SonarQube, which are widely used in modern software development workflows.

The pipeline begins immediately after the active scan rules have been executed and their findings collected. Each rule, whether it is a custom-defined rule or one from an external library (e.g., OWASP ZAP, OpenVAS), contributes its findings to a centralized result repository. This repository is typically implemented as a map or tree structure, where each key corresponds to a unique identifier for the vulnerability and the value contains all relevant metadata such as the rule name, the URL where the vulnerability was found, the type of vulnerability (e.g., SQL injection, XSS), and the confidence level. The data model is intentionally designed to be both granular and extensible, allowing for the inclusion of additional context such as HTTP headers, request/response bodies, and even the exact line numbers in source code if applicable.

Once all findings have been aggregated, the pipeline initiates the SARIF emission process. This involves mapping the internal result structure to the SARIF schema, which is defined in JSON format with a specific set of required and optional fields. The process begins by creating a new SARIF file, which is initialized with a default configuration that includes the tool name, version, and an empty list of runs. Each run corresponds to a distinct scan instance, which may be further partitioned into separate runs based on the target application, environment, or authentication context. This granular approach ensures that each run can be independently analyzed, audited, or integrated into CI/CD pipelines.

The mapping from internal result data to SARIF is a multi-step process that involves several key transformations. First, each vulnerability is converted into a `result` object within the SARIF file. The `result` object contains essential information such as the `ruleId`, which is derived from the active scan rule’s identifier, the `message` that describes the vulnerability, and the `location` where the vulnerability was detected. The `location` includes the `physicalLocation` with details about the URL, the request method, and the exact path or endpoint where the vulnerability occurred. Additionally, the `location` may also include the `artifactLocation`, which provides contextual information such as the source code file or API endpoint definition if available.

To ensure consistency and clarity, the pipeline applies a set of transformation rules that standardize the metadata associated with each result. For example, if a rule generates multiple findings for the same URL but different endpoints, the pipeline ensures that each finding is uniquely identified by its endpoint path. Similarly, if a vulnerability has multiple severity levels based on the rule’s configuration, the pipeline applies a resolution strategy to select the highest severity level as the default, while preserving the ability to track lower-severity instances separately. This approach balances precision with usability, ensuring that users can quickly identify high-priority issues without being overwhelmed by lower-severity findings.
