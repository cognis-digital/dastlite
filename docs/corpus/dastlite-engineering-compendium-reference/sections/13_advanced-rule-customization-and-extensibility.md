### Rule Syntax and Structure

The rule syntax and structure in dastlite are meticulously designed to ensure clarity, extensibility, and precision in defining active scan rules. At its core, a dastlite rule is structured as a JSON object that encapsulates the rule’s metadata, conditions, actions, and configuration parameters. This design allows for both human readability and machine processing, enabling seamless integration with dastlite’s runtime engine. Each rule comprises several key components: `id`, `name`, `description`, `severity`, `tags`, `match`, `actions`, and `config`. These elements collectively define the behavior, scope, and impact of the rule during a scan.

The `id` field serves as a unique identifier for the rule, ensuring that each rule can be referenced unambiguously within dastlite’s configuration and execution environment. This identifier is typically a string in the format `namespace.rule`, where `namespace` denotes the rule set or module to which the rule belongs. For example, a rule might have an `id` of `security.owasp-top10-2021.xss`, indicating that it belongs to the OWASP Top 10 2021 rule set and is focused on cross-site scripting (XSS) vulnerabilities. This hierarchical structure not only aids in organization but also facilitates filtering and categorization during runtime.

The `name` field provides a human-readable label for the rule, making it easier for users to identify and manage rules within the dastlite ecosystem. The `description` field offers a more detailed explanation of the rule’s purpose, its expected behavior, and the conditions under which it should be triggered. This description is critical for maintaining clarity, especially when rules are shared across teams or integrated into larger rule sets. The `severity` field defines the priority level of the rule, typically ranging from `low`, `medium`, to `high`, and is used by dastlite’s reporting and triage mechanisms to prioritize findings.

The `tags` field allows for flexible categorization of rules, enabling users to apply filters based on specific criteria such as vulnerability type, technology stack, or compliance standard. For instance, a rule might be tagged with `xss`, `owasp-top10`, and `web-app`, allowing users to quickly locate relevant rules during configuration or post-scan analysis. This tagging system is integral to dastlite’s extensibility, as it supports dynamic rule grouping and filtering without requiring changes to the rule itself.

The `match` field defines the conditions under which a rule should be triggered. It is a JSON object that specifies patterns, headers, payloads, or other contextual data that the rule should evaluate against during a scan. The `match` mechanism in dastlite is highly flexible, supporting both regular expressions and structured query language (SQL)-inspired syntax for pattern matching. For example, a rule might specify a `match` condition that checks if a response contains a specific HTTP status code or if a particular header is present. This allows for precise control over when a rule is activated, ensuring that only relevant findings are reported.

The `actions` field outlines the steps dastlite should take when a rule is triggered. These actions can include logging the finding, marking it as a false positive, or emitting a structured report in SARIF format. The `actions` field is essential for defining the impact of a rule and ensuring that findings are processed according to predefined workflows. For instance, a high-severity rule might trigger an action to emit a SARIF record with detailed metadata, while a low-severity rule might simply log the finding without further processing.

The `config` field provides additional parameters that fine-tune the behavior of a rule. This can include timeouts, thresholds, or other configuration options that influence how the rule is executed. The `config` field is particularly useful for customizing rules to suit specific environments or requirements. For example, a rule might have a `config` parameter that specifies a maximum response size to consider as a potential vulnerability, allowing users to adjust the sensitivity of the rule based on their needs.

The syntax and structure of dastlite rules are designed to be both expressive and extensible, enabling developers and security professionals to create, modify, and combine rules with ease. The use of JSON as the primary format ensures that rules are easy to parse, validate, and integrate into larger configurations. Additionally, the modular nature of the rule syntax allows for the creation of reusable components, such as shared conditions or actions, which can be leveraged across multiple rules.

The extensibility of dastlite’s rule syntax is further enhanced by its support for custom types and plugins. Users can define new data types or functions that are specific to their environment or use case, allowing for greater flexibility in rule creation. For example, a custom function might be defined to parse application-specific headers or to evaluate complex business logic that is not covered by the built-in mechanisms. This capability enables dastlite to adapt to a wide range of use cases and environments, from traditional web applications to modern mobile APIs.

In summary, the rule syntax and structure in dastlite are meticulously designed to ensure clarity, extensibility, and precision in defining active scan rules. By leveraging JSON as the primary format, dastlite provides a flexible and modular approach to rule creation, allowing users to define, customize, and combine rules with ease. The structured components of each rule—such as `id`, `name`, `description`, `severity`, `tags`, `match`, `actions`, and `config`—collectively define the behavior, scope, and impact of the rule during a scan. This design not only facilitates precise control over the scanning process but also supports dynamic configuration and integration with larger rule sets, making dastlite a powerful tool for active security testing.

### Rule Metadata and Configuration

Rule metadata and configuration form the backbone of extensible active scanning in dastlite, enabling precise control over rule behavior, contextual applicability, and integration with broader CI/CD pipelines. At its core, a rule in dastlite is defined by a structured YAML file that encapsulates metadata, configuration parameters, and execution logic. This metadata includes the rule’s identifier, name, description, severity, and a set of configurable parameters that dictate how the rule is triggered, what payloads are used, and how responses are evaluated. The configuration extends beyond static definitions to include dynamic values such as URL templates, headers, and authentication tokens, allowing rules to adapt to varying environments.

A fundamental aspect of rule metadata is the `id` field, which serves as a unique identifier for the rule within the dastlite ecosystem. This identifier is crucial for tracking, logging, and deduplication of findings. For instance, a rule targeting SQL injection might have an ID like `sql-injection-001`, ensuring that any instance of this rule firing across different targets can be uniquely referenced. The `name` field complements the ID by providing a human-readable label, which is essential for readability in logs and user-facing reports. The `description` further enriches the metadata by offering context on the rule’s purpose, such as “Detects SQL injection vulnerabilities through malformed input parameters.”

Severity classification, defined under the `severity` key, plays a pivotal role in prioritizing findings. dastlite supports standard severity levels such as `low`, `medium`, `high`, and `critical`, which align with industry standards like OWASP’s Top Ten. For example, a rule detecting cross-site scripting (XSS) might be assigned a severity of `high` due to its potential for user data exposure. This classification not only aids in triaging findings but also integrates seamlessly with tools like GitHub Advanced Security and Azure DevOps, which use severity levels to prioritize remediation efforts.

Configuration parameters are where the flexibility of dastlite’s rule system truly shines. These parameters are defined under a `config` section within the YAML file and can include URL templates, request payloads, headers, and authentication tokens. For instance, a rule targeting authentication bypass might define a URL template like `https://target.com/api/login?username={username}&password={password}` with dynamic placeholders for `username` and `password`. This allows the rule to be applied across multiple endpoints without requiring manual reconfiguration for each target. Similarly, headers such as `Content-Type` or `Authorization` can be dynamically injected based on the target’s requirements, ensuring that the scan mimics real user interactions.

One of the most powerful features of configuration is the ability to define payloads and payloads templates. Payloads are specific input values that the rule injects into the request to trigger potential vulnerabilities. For example, a SQL injection rule might include payloads like `' OR '1'='1` or `'; DROP TABLE users;--`, which are tested against the target’s endpoints. Payloads can be static, as in the above examples, or dynamic, using placeholders that are resolved at runtime based on the target’s context. This dynamic resolution ensures that the rule remains adaptable to different environments and configurations.

The `payloads` section within a rule’s YAML file allows for the definition of multiple payloads, each with its own set of parameters. For instance, a rule might define two payloads: one for testing SQL injection and another for testing command injection. Each payload can have associated metadata such as `description`, `expected_response`, and `match_criteria`, which guide the rule’s execution and evaluation. This level of granularity enables precise control over how each payload is applied and interpreted during the scan.

Another critical component of rule configuration is the `headers` section, which defines HTTP headers to be included in the request. These headers can include standard ones like `User-Agent`, `Accept`, and `Content-Type`, as well as custom headers specific to the target application. For example, a rule targeting an API might require the `Authorization` header with a bearer token, ensuring that the scan authenticates as a valid user. This configuration not only improves the accuracy of the scan but also reduces false positives by mimicking real-world authentication scenarios.

Authentication tokens are another key aspect of rule configuration, particularly for authenticated scans. dastlite supports various authentication mechanisms, including Basic Auth, OAuth2, and API keys, which can be dynamically injected into the request headers based on the target’s requirements. For instance, a rule targeting an internal API might require an `Authorization` header with a bearer token obtained from a secrets manager like HashiCorp Vault or AWS Secrets Manager. This dynamic injection ensures that the scan has the necessary permissions to access protected endpoints, thereby improving the depth and accuracy of the findings.

In addition to static configurations, dastlite allows for dynamic configuration through environment variables and external data sources. For example, a rule might reference an environment variable `TARGET_URL` to dynamically set the base URL for the scan. This flexibility enables rules to be reused across different environments without requiring manual changes. Furthermore, external data sources such as JSON files or API endpoints can be integrated into the configuration, allowing for more complex and context-aware rule execution.

The `match_criteria` section within a rule’s YAML file defines how the response from the target is evaluated to determine if a vulnerability has been found. This section includes parameters such as `status_code`, `response_body`, `headers`, and `time_taken`, which are used to filter and validate the response. For example, a rule detecting an insecure direct object reference (IDOR) might require a response status code of `200` and a response body containing the string `user123`. This precise matching ensures that only relevant findings are reported, reducing noise and improving the reliability of the scan.

Finally, the `deduplication` section within the rule’s YAML file allows for the configuration of deduplication rules, ensuring that identical findings are not reported multiple times. This includes parameters such as `fingerprint`, `context`, and `threshold`, which define how findings are compared and grouped. For instance, a rule might use the fingerprint `request_url` to group findings based on the URL they were triggered from, preventing redundant reports for the same vulnerability. This deduplication mechanism is crucial for maintaining the quality and usability of the scan results, particularly in large-scale environments where multiple scans are performed.

In summary, rule metadata and configuration in dastlite provide a robust framework for defining, customizing, and executing active scanning rules. By leveraging structured YAML files, dynamic parameters, and precise match criteria, dastlite enables developers and security teams to create highly targeted and adaptable rules that integrate seamlessly with their existing workflows. This level of configurability not only enhances the accuracy and depth of the scan but also ensures that findings are actionable, prioritized, and easily integrated into broader CI/CD pipelines.

### Conditional Rule Triggers and Context Matching

Conditional rule triggers and context matching are fundamental to enabling dynamic and context-aware active scanning in dastlite. These mechanisms allow rules to be activated based on specific conditions derived from the runtime state of the scan environment, such as HTTP headers, request parameters, response content, or authentication tokens. By leveraging these triggers, dastlite can execute rules only when relevant, reducing false positives and improving scan efficiency. This section explores how conditional rule triggers are implemented, the syntax and semantics of context matching, and how they enable advanced rule customization.

At the core of conditional rule triggers in dastlite is the ability to define predicates that evaluate runtime data during a scan. These predicates can be based on HTTP headers, query parameters, cookies, response bodies, or even application-specific metadata. For example, a rule might be configured to trigger only when the `User-Agent` header contains the string `"Mozilla/5.0 (X11; Linux x86_64)"`, indicating a specific browser or device type. Another rule could activate if the `Authorization` header includes a bearer token with a specific scope, such as `"read:users"`. These conditions are expressed using a declarative syntax that integrates seamlessly with dastlite’s rule configuration model.

The implementation of these triggers relies on a combination of pattern matching and conditional logic. dastlite uses regular expressions and JSON path expressions to extract and evaluate data from HTTP messages. For instance, the `match` keyword in a rule can be used to specify a pattern that must match against a specific field, such as the `Content-Type` header or a JSON payload. If the condition is met, the associated rule action (e.g., sending a request, inspecting a response) is executed. This approach ensures that rules are only applied when their context is relevant, reducing unnecessary network traffic and resource consumption.

Context matching in dastlite is further enhanced by the ability to reference dynamic values from the scan environment. For example, if a rule is designed to test for an insecure HTTP endpoint, it can be configured to trigger only when the current request is made over HTTPS. This is achieved using the `context` keyword, which allows the rule to access variables such as `request.scheme`, `response.status`, or `session.auth_token`. These variables are populated dynamically during the scan and provide real-time data for evaluating conditions.

One of the key mechanisms enabling context matching is the use of JSON path expressions. dastlite supports a subset of the JSON Pointer syntax, allowing rules to target specific fields within JSON payloads. For instance, a rule might be configured to trigger if the `user.role` field in a response body contains the value `"admin"`, indicating that an administrative endpoint has been accessed. This level of specificity is crucial for tailoring rules to particular application behaviors and ensuring that they are applied only when appropriate.

In addition to static pattern matching, dastlite supports conditional logic through the use of boolean expressions. These expressions can combine multiple conditions using logical operators such as `AND`, `OR`, and `NOT`. For example, a rule might be configured to trigger only if the request path starts with `/api/v1/` **and** the `Content-Type` header is `application/json`. This allows for highly granular control over when rules are executed, ensuring that they are applied in the correct context.

The integration of conditional triggers and context matching also extends to the use of environment variables and configuration parameters. Rules can be parameterized to accept values from external sources, such as a secrets manager or a configuration file. This enables rules to be reused across different environments while maintaining the ability to adapt to specific conditions. For example, a rule that tests for a particular API endpoint might be configured to use a dynamic base URL derived from an environment variable, allowing it to work across staging and production environments without modification.

Another important aspect of conditional rule triggers is their ability to handle nested or hierarchical data structures. dastlite provides mechanisms for traversing complex JSON or XML payloads using dot notation or XPath expressions. This allows rules to evaluate conditions based on deeply nested fields, such as `response.body.data.items[0].id`, which could represent an identifier for a specific resource in a RESTful API. By supporting these advanced data access patterns, dastlite ensures that rules can be applied to a wide range of application architectures and data formats.

The use of conditional triggers also enables the implementation of stateful scanning logic. For example, a rule might be configured to trigger only if a previous request has successfully authenticated the user. This is achieved by referencing the `session.authenticated` flag, which is set during the authentication phase of the scan. Such state-aware rules are particularly useful in applications that require session management or token-based authentication, as they ensure that scanning activities are aligned with the actual user interaction flow.

In addition to runtime conditions, dastlite supports conditional triggers based on the results of previous rule executions. For instance, a rule might be configured to trigger only if a preceding rule has identified a specific vulnerability type, such as an insecure cookie. This allows for the creation of cascading rules that respond to the outcomes of earlier checks, enabling more sophisticated scanning strategies. These dependencies are managed through a rule execution graph, which ensures that conditions are evaluated in the correct order and context.

The combination of conditional triggers and context matching also facilitates the use of custom rule libraries and plugins. Developers can define reusable rule components that encapsulate specific conditions and actions, which can then be composed into larger scanning workflows. For example, a plugin might provide a set of pre-defined conditions for checking authentication headers, which can be combined with other rules to create a comprehensive scanning strategy. This modular approach enhances the extensibility of dastlite and allows for rapid adaptation to new security requirements or application architectures.

In summary, conditional rule triggers and context matching are essential components of dastlite’s advanced rule customization capabilities. By enabling rules to be executed based on dynamic conditions derived from the scan environment, dastlite ensures that active scanning is both efficient and effective. These mechanisms allow for precise control over when and how rules are applied, reducing false positives and improving the overall quality of the scan results. Through the use of pattern matching, boolean logic, JSON path expressions, and state-aware conditions, dastlite provides a flexible and powerful framework for tailoring active scanning to specific application contexts and security requirements.

This ensures that any new or modified rules are immediately available for scanning, reducing the latency between rule development and deployment.     path: /rules
```yaml
    version: v1.2.0
```

This approach not only reduces redundancy but also makes it easier to update or modify the configuration in the future.

The integration of external rule repositories is further enhanced by dastlite's support for rule metadata and documentation. Each rule repository can include a `metadata` directory that contains information about the rules, such as their purpose, supported technologies, and any dependencies they require. This metadata is used by dastlite to provide context and guidance when applying the rules, ensuring that users understand how each rule functions and what it is designed to detect.

In summary, the integration of external rule repositories into dastlite is a robust and flexible mechanism that enables dynamic rule management, version control, and seamless collaboration across development teams.
