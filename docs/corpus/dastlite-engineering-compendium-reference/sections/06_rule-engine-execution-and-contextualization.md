## 6. Rule Engine Execution and Contextualization

### Rule Matching and Pattern Recognition

The core function of a rule engine in a DAST runner like dastlite is to match patterns within the extracted response data against predefined active-scan rules. This process is not merely a matter of syntactic comparison but involves a layered approach that leverages both static and dynamic analysis techniques. Rule matching begins with the parsing of HTTP responses, which are typically structured as JSON or XML documents, and may also include text-based content such as HTML or plain text. Each response is tokenized into its constituent parts—headers, status codes, body content—and these components are then compared against rule patterns defined in a ruleset. The ruleset is a collection of structured definitions that describe specific vulnerabilities or potential issues, often including regular expressions, XPath queries, or JSONPath expressions to capture the expected patterns.

The matching process is governed by a set of well-defined algorithms and data structures that ensure efficiency and accuracy. For example, regular expressions are used extensively to match string patterns within response bodies. These expressions can be anchored to specific parts of the document or span across multiple lines. In cases where the target content is structured in XML or JSON, XPath or JSONPath queries are employed to navigate the document tree and extract relevant nodes for comparison. These queries allow for precise targeting of elements that may indicate a vulnerability, such as an exposed API key or a misconfigured cookie.

One of the key challenges in rule matching is handling variations in response formats. For instance, a single endpoint might return different JSON structures based on user input or system state. To address this, dastlite employs a contextualization layer that dynamically adjusts the ruleset based on the current execution context. This includes factors such as the authentication state, the presence of specific headers, and the content type of the response. The contextualization engine uses a combination of static analysis of the API surface and dynamic runtime data to determine which rules are most relevant for a given request.

Another critical aspect of rule matching is the use of heuristics and machine learning techniques to improve accuracy over time. While traditional rule-based systems rely on predefined patterns, dastlite incorporates a feedback loop that allows the system to learn from false positives and false negatives. This is achieved through a mechanism known as "rule adaptation," where the system analyzes historical data to refine its matching criteria. For example, if a particular rule consistently produces false positives in certain contexts, the system can adjust the pattern or add additional conditions to reduce the likelihood of incorrect matches.

The efficiency of rule matching is further enhanced by the use of indexing and caching mechanisms. The dastlite engine maintains an index of frequently accessed endpoints and their associated response structures, allowing for rapid lookup and comparison. This is particularly useful in large-scale API surfaces where the number of endpoints can be in the thousands. By precomputing and storing relevant information, the system minimizes redundant processing and ensures that each rule match is performed as efficiently as possible.

Pattern recognition within the rule matching process extends beyond simple string or structure comparisons. It involves the identification of semantic patterns that may indicate a vulnerability, even if they do not strictly conform to the predefined rules. For example, a rule might be designed to detect an exposed API key, but in some cases, the key might be embedded within a larger string or encoded using a non-standard format. In such scenarios, dastlite employs a combination of regular expressions and semantic analysis to identify the key, even if it is not immediately apparent.

To handle these complex cases, dastlite integrates with external libraries and tools that provide advanced pattern recognition capabilities. For instance, the system may utilize natural language processing (NLP) techniques to analyze text-based responses for patterns such as sensitive information or insecure configurations. These techniques are particularly useful when dealing with unstructured data or when the target content is not easily parseable using traditional methods.

The rule matching process also includes a mechanism for handling dynamic content, where the response may change based on external factors such as time, user input, or system state. In these cases, dastlite employs a temporal analysis approach that tracks changes over time and compares them against expected patterns. This is especially important in scenarios where vulnerabilities are time-dependent, such as those related to session fixation or token expiration.

To ensure the reliability of rule matching, dastlite incorporates a validation layer that checks the consistency of the matched patterns against the original response data. This involves verifying that the extracted information aligns with the expected structure and content, and that there are no mismatches due to parsing errors or data corruption. The validation process also includes checking for edge cases and ensuring that the ruleset is applied consistently across different environments and configurations.

In addition to these technical mechanisms, dastlite employs a modular architecture that allows for the easy integration of new rules and pattern recognition techniques. This modularity ensures that the system can evolve alongside emerging threats and technologies, without requiring a complete overhaul of the rule engine. For example, new rules can be added to detect vulnerabilities specific to certain frameworks or protocols, while existing rules can be refined based on user feedback and performance metrics.

The rule matching and pattern recognition capabilities of dastlite are further enhanced by its ability to handle multi-step interactions and complex workflows. In some cases, a vulnerability may only become apparent after a series of requests and responses, requiring the system to track state across multiple steps. This is achieved through a state management module that maintains context information for each session and ensures that rules are applied in the correct sequence.

Overall, the rule matching and pattern recognition process in dastlite is a sophisticated interplay of static and dynamic analysis techniques, contextualization, and adaptive learning. By leveraging a combination of structured patterns, semantic analysis, and real-time validation, the system ensures that vulnerabilities are detected with high accuracy and efficiency. This foundational capability underpins the broader functionality of the dastlite DAST runner, enabling it to effectively crawl and analyze authenticated web and mobile API surfaces while emitting deduplicated SARIF reports for comprehensive vulnerability assessment.

### Contextual Rule Activation and Deactivation

Contextual Rule Activation and Deactivation is a fundamental mechanism in the dastlite rule engine, enabling dynamic adaptation of active scan rules based on runtime context. This process ensures that only relevant rules are executed at any given moment, optimizing performance, reducing false positives, and increasing the precision of security assessments. The activation and deactivation of rules are governed by a combination of static metadata, runtime conditions, and contextual data derived from the current state of the application under test (AUT). These mechanisms are deeply integrated into the execution pipeline, allowing for fine-grained control over which rules are applied during each request.

At the core of this mechanism is the **Rule Contextualizer**, a component responsible for evaluating the state of the system and determining which rules should be active. The Rule Contextualizer operates on a set of predefined **contextual triggers**—conditions that, when met, activate or deactivate specific rules. These triggers can be based on various factors, including the HTTP method used (GET, POST, PUT, DELETE), the presence of certain headers, the content type of the request or response, the authentication state, and even the URL path. For instance, a rule designed to detect insecure direct object references (IDOR) might only be activated when the request is a GET operation targeting a resource with an identifier parameter. This ensures that the rule is applied in scenarios where it is most likely to produce a meaningful result, rather than being triggered indiscriminately across all requests.

The activation of rules is also influenced by **rule dependencies**, which define relationships between different rules. For example, a rule that checks for insecure HTTP headers might be dependent on the presence of an authentication token in the request. If the authentication token is not present, the rule may be deactivated to avoid unnecessary processing. Similarly, some rules are conditionally activated based on the outcome of other rules. This allows for a hierarchical approach to rule execution, where certain rules are only executed if others have already identified specific conditions in the application's behavior.

Another key aspect of contextual rule activation is **dynamic rule prioritization**, which adjusts the order in which rules are applied based on the current context. For example, during an authenticated session, rules related to session management or token validation may be prioritized over general security checks. This prioritization is managed through a **rule priority matrix**, which assigns weights to rules based on their relevance to the current state of the application. The matrix can be static, defined in the rule metadata, or dynamic, updated in real-time based on runtime data. This allows for adaptive behavior, where the rule engine can shift focus depending on the nature of the request and the environment in which it is executed.

The deactivation of rules is equally important, as it prevents unnecessary processing and reduces resource consumption. Rules are deactivated when their contextual triggers no longer apply or when they have been determined to be irrelevant based on previous execution outcomes. For example, a rule that checks for SQL injection might be deactivated after a successful login request where the input is sanitized, as the risk of SQL injection is reduced in that context. This deactivation is often managed through **rule lifecycle hooks**, which are callbacks executed when a rule is activated or deactivated. These hooks allow for additional processing, such as logging, metric collection, or triggering follow-up actions based on the rule's state.

A concrete example of contextual rule activation and deactivation can be found in the handling of **OAuth2 token validation rules**. When an application uses OAuth2 for authentication, certain rules are only relevant during specific phases of the authentication flow. For instance, a rule that checks for token expiration is activated when a request includes an access token in the Authorization header. However, if the same token is used in a subsequent request, the rule may be deactivated once the token has been validated and the session is considered active. This ensures that the rule is only applied when it is most likely to identify a valid issue, such as an expired or invalid token.

The Rule Contextualizer also leverages **runtime metadata** to make decisions about rule activation. This metadata includes information such as the current user's role, the application version, and the environment (e.g., staging, production). For example, a rule that checks for deprecated APIs might be activated only in environments where the application is running a specific version or when the user has a particular role. This allows for context-aware scanning, where rules are tailored to the specific needs of the application and its users.

In addition to static and dynamic triggers, the Rule Contextualizer supports **conditional expressions** that allow for more complex logic in determining rule activation. These expressions can be written in a domain-specific language (DSL) or as inline code snippets, enabling fine-grained control over when a rule is applied. For instance, a rule might only be activated if the request URL contains a certain parameter and the response status code is 200. This level of customization allows for precise targeting of security issues without overwhelming the system with unnecessary checks.

The integration of contextual rule activation and deactivation into the dastlite execution pipeline ensures that the rule engine remains both efficient and effective. By dynamically adjusting which rules are applied based on real-time context, the system can adapt to the specific characteristics of the application under test, leading to more accurate and actionable results. This mechanism is further enhanced by **logging and telemetry**, which provide visibility into how and when rules are activated or deactivated. These logs can be used for post-scan analysis, helping to refine the rule set over time and improve the overall effectiveness of the security assessment.

In summary, Contextual Rule Activation and Deactivation in dastlite is a sophisticated mechanism that ensures rules are applied only when they are most relevant. Through the use of contextual triggers, rule dependencies, dynamic prioritization, and runtime metadata, the rule engine can adapt to the specific needs of the application under test. This not only improves the efficiency of the scanning process but also enhances the accuracy of the results, making dastlite a powerful tool for modern security assessments.

### Dynamic Rule Prioritization and Weighting

Dynamic Rule Prioritization and Weighting is a core mechanism within the dastlite rule engine, designed to adaptively assign relevance and urgency to each active scan rule based on runtime context. This process ensures that rules are not applied uniformly but are instead weighted according to factors such as asset criticality, historical vulnerability patterns, and real-time system behavior. By integrating contextual metadata with rule execution logic, dastlite enables a more targeted and efficient vulnerability assessment, reducing false positives while maximizing coverage of high-risk issues.

At the heart of dynamic rule prioritization is the concept of **contextual weighting**, which involves assigning numerical weights to rules based on their likelihood of triggering a true positive in the current environment. These weights are calculated using a combination of static metadata (such as rule category, severity level, and known false positive rates) and dynamic data (such as the current application’s authentication state, API response patterns, and historical scan results). For example, a rule that identifies SQL injection vulnerabilities might be weighted higher in a database-heavy microservice but lower in a lightweight REST API endpoint. This allows dastlite to prioritize rules that are most likely to produce actionable findings in the specific environment being scanned.

The rule engine employs **machine learning models** trained on historical scan data to predict the relevance of each rule in a given context. These models are built using labeled datasets that include information about successful and false positive findings, along with metadata such as the target application’s architecture, API endpoints, and authentication methods. The training process involves feature extraction from both the rules themselves (e.g., regex patterns, HTTP methods, and payload structures) and the runtime environment (e.g., response times, HTTP status codes, and session management behaviors). Once trained, these models are deployed as **contextual classifiers** within the rule engine, which dynamically adjust rule weights in real time based on the current scan context.

One of the key mechanisms enabling dynamic weighting is the **rule fitness score**, a metric that quantifies how well a given rule aligns with the current environment. The fitness score is calculated using a weighted sum of several factors, including:

1. **Rule relevance**: A measure of how well the rule’s pattern matches the current request structure (e.g., URL path, HTTP method, or payload content).
2. **Asset criticality**: A value derived from the target application’s business impact, such as whether it handles sensitive data or supports mission-critical operations.
3. **Historical performance**: A metric based on past scan results, indicating how often the rule has produced true positives versus false positives in similar environments.
4. **Runtime behavior**: Real-time data collected during the scan, such as response times, HTTP status codes, and session token lifetimes.

For instance, during a scan of a financial API, the rule for detecting insecure direct object references (IDOR) might receive a higher fitness score if the API endpoint includes parameters that are frequently manipulated in a way that exposes sensitive data. Conversely, in a simple public-facing API with minimal user interaction, the same rule might be downweighted due to its lower likelihood of triggering a true positive.

The rule engine also incorporates **context-aware suppression logic**, which allows certain rules to be temporarily disabled or reduced in weight based on specific conditions. For example, if a scan detects that a particular endpoint consistently returns 404 errors, the rule for identifying missing HTTP headers might be suppressed to avoid generating unnecessary false positives. This suppression is not static but is instead recalculated dynamically as the scan progresses, ensuring that the rule engine adapts to changing conditions in real time.

Another critical component of dynamic weighting is **rule dependency analysis**, which evaluates how the performance of one rule may impact others. For instance, if a rule for detecting Cross-Site Scripting (XSS) is applied to a large number of endpoints and generates a high volume of alerts, the rule engine might reduce its weight temporarily to prevent overwhelming the user with false positives. This analysis is performed using a graph-based approach, where each rule is represented as a node, and edges represent dependencies or interactions between rules. By analyzing these relationships, the engine can optimize the overall scan efficiency while maintaining high detection accuracy.

To further refine dynamic weighting, dastlite integrates **real-time feedback loops** that allow the rule engine to learn from its own execution. After each scan, the system analyzes the results and updates the weights of rules based on their performance in the current context. For example, if a rule for detecting insecure HTTP methods (e.g., HTTP 1.0) is found to generate many false positives in a modern API environment, its weight is reduced in subsequent scans. Conversely, if a rule for identifying outdated TLS versions is frequently validated as a true positive, its weight is increased to ensure it remains a high-priority rule.

This feedback mechanism is supported by a **rule performance dashboard**, which provides detailed metrics on each rule’s effectiveness, including the number of true positives, false positives, and missed vulnerabilities. These metrics are used to train the machine learning models that underpin the dynamic weighting system, ensuring continuous improvement over time. Additionally, the dashboard allows users to manually adjust rule weights based on their own insights or organizational priorities, providing a hybrid model of automated and human-informed prioritization.

In practice, dynamic rule prioritization and weighting significantly enhance the efficiency and accuracy of dastlite’s active scan process. By focusing resources on rules that are most likely to produce actionable findings in the current environment, the system reduces the noise of false positives while maintaining high coverage of critical vulnerabilities. This approach is particularly valuable in complex, multi-tiered architectures where a one-size-fits-all rule application would lead to excessive alerts and missed issues.

A concrete example of this mechanism in action can be seen in the dastlite scan of a healthcare API that handles patient records. During the scan, the system identifies that the API uses OAuth 2.0 for authentication, which implies that session tokens are managed through a centralized identity provider. In this context, the rule for detecting insecure session management (e.g., weak token encryption or lack of refresh tokens) is weighted higher due to the increased risk of token theft. Meanwhile, rules targeting older vulnerabilities like SQL injection are downweighted because the API uses parameterized queries and has a robust ORM layer. As the scan progresses, the system dynamically adjusts weights based on real-time data, such as the number of endpoints accessed and the response patterns observed, ensuring that the most relevant rules are applied at each stage.

The dynamic weighting mechanism also supports **rule chaining**, where the output of one rule can influence the weight of another. For example, if a rule identifies a potential vulnerability in an authentication endpoint, subsequent rules related to session management or token validation might be prioritized to investigate deeper into the same area. This chaining effect allows the rule engine to focus on interconnected issues, improving the overall effectiveness of the scan.

In summary, dynamic rule prioritization and weighting is a sophisticated mechanism that enables dastlite’s rule engine to adaptively apply rules based on runtime context. By integrating machine learning models, contextual classifiers, and real-time feedback loops, the system ensures that each rule is weighted appropriately to maximize detection accuracy while minimizing false positives. This approach not only enhances the efficiency of the active scan process but also provides a more targeted and actionable vulnerability assessment, making dastlite a powerful tool for modern application security testing.

### Rule Execution Environment Configuration

The Rule Execution Environment (REE) is a foundational component of dastlite’s architecture, serving as the runtime context in which active scan rules are executed. Unlike traditional DAST tools that rely on monolithic rule engines or external rule repositories, dastlite employs a modular and extensible REE that is tightly integrated with the overall system. This environment is designed to provide a consistent, isolated, and configurable execution space for each rule, ensuring predictable behavior across diverse targets and environments. The REE abstracts away low-level implementation details such as network connectivity, authentication handling, and response parsing, allowing rules to focus on their specific logic without concern for infrastructure specifics.

At the heart of the REE is a lightweight, sandboxed runtime that isolates each rule execution from the host system. This isolation is achieved through a combination of containerization and process-level sandboxing mechanisms. For instance, dastlite leverages Docker containers to encapsulate each rule’s execution environment, ensuring that dependencies such as specific libraries or network configurations are self-contained. Within these containers, the REE provides a standardized runtime environment with access to core utilities, logging services, and configuration management tools. This approach not only enhances security by limiting the attack surface of each rule but also ensures reproducibility across different execution contexts.

The REE is further augmented by a dynamic configuration system that allows for fine-grained control over rule behavior. This system is based on a declarative configuration model, where each rule can define its own set of parameters, dependencies, and execution constraints. These configurations are stored in a structured format, such as JSON or YAML, and are loaded at runtime to tailor the REE to the specific requirements of the rule. For example, a rule designed to test for insecure HTTP headers might specify a configuration that includes the allowed header types, the maximum number of requests to perform, and the timeout duration for each request. This flexibility enables rules to adapt to varying target environments without requiring code changes.

The REE also incorporates a robust logging and diagnostics framework to provide detailed insights into rule execution. Each rule execution is logged with timestamps, status codes, and contextual information such as the target URL, HTTP method, and response payload. These logs are stored in a centralized repository, allowing for post-execution analysis and debugging. In addition, the REE supports real-time monitoring and alerts, enabling administrators to quickly identify and address issues during active scan operations. For example, if a rule encounters an unexpected error or a resource exhaustion condition, the REE can trigger an alert to notify the appropriate team.

To ensure consistency and interoperability, the REE is designed to support multiple execution models, including synchronous and asynchronous processing. Synchronous execution is used for rules that require immediate feedback or have deterministic outcomes, such as checking for specific response codes or content types. Asynchronous execution, on the other hand, is employed for rules that may involve prolonged operations or external dependencies, such as querying a database or invoking a third-party API. This dual-model approach allows the REE to handle a wide range of rule complexities while maintaining performance and scalability.

The REE also integrates with dastlite’s configuration-as-code framework, enabling rule execution environments to be defined and managed through declarative configuration files. These files are version-controlled and can be deployed across different environments, ensuring that rule behavior remains consistent across development, testing, and production. For example, a configuration file might define the REE parameters for a specific rule, including the required libraries, environment variables, and resource limits. This integration simplifies the management of complex rule execution scenarios and reduces the risk of configuration drift.

In addition to its runtime capabilities, the REE is designed to support extensibility through plugin architecture. This allows developers to add custom modules or utilities that enhance the functionality of the REE without modifying the core framework. For instance, a plugin might provide additional logging capabilities, integrate with external monitoring tools, or enable advanced resource management features. The plugin system is implemented using a modular design, where each plugin is encapsulated in a separate module and can be dynamically loaded at runtime. This extensibility ensures that the REE can evolve alongside the rule set, accommodating new requirements and technologies as they emerge.

The REE also plays a critical role in ensuring the accuracy and reliability of rule execution by providing a consistent interface for interacting with the target system. This interface abstracts away the complexities of network communication, authentication, and response parsing, allowing rules to focus on their specific logic. For example, when a rule needs to send an HTTP request, it interacts with the REE’s abstraction layer, which handles the underlying network operations, including establishing connections, sending requests, and receiving responses. This abstraction not only simplifies the development of rules but also ensures that the REE can adapt to different target environments without requiring changes to the rule logic.

To further enhance the reliability of rule execution, the REE includes a built-in mechanism for handling errors and exceptions. When a rule encounters an error, such as a network timeout or a malformed response, the REE logs the error and provides detailed diagnostic information to aid in troubleshooting. Additionally, the REE supports configurable retry policies, allowing rules to attempt failed operations a specified number of times before marking them as failed. This feature is particularly useful for rules that may encounter transient issues, such as temporary network outages or rate limiting by the target server.

The REE also incorporates a resource management system to optimize performance and prevent resource exhaustion during large-scale active scan operations. This system dynamically allocates resources such as memory, CPU, and network bandwidth based on the current workload and the requirements of each rule. For example, resource-intensive rules may be allocated more memory or processing power to ensure they complete within the expected timeframe, while lightweight rules may share resources more efficiently. This dynamic allocation ensures that the REE can handle a large number of concurrent rule executions without degrading overall system performance.

In summary, the Rule Execution Environment in dastlite is a meticulously designed and highly configurable component that provides the runtime context for active scan rules. By leveraging containerization, dynamic configuration, and extensibility, the REE ensures consistent, reliable, and scalable execution of rules across diverse environments. Its integration with dastlite’s configuration-as-code framework and support for multiple execution models further enhance its adaptability and maintainability. Through robust logging, error handling, and resource management, the REE not only simplifies the development of rules but also ensures that they operate efficiently and effectively in real-world scenarios. This foundation enables dastlite to deliver accurate and actionable results while maintaining the flexibility needed to evolve with changing security landscapes and technological advancements.

### Inter-Scan Rule Dependency Management

The management of inter-scan rule dependencies is a critical component of the dastlite rule engine, ensuring that scan results are both accurate and contextually relevant across multiple execution cycles. At its core, this mechanism addresses the challenge of maintaining consistency and coherence in scan outcomes when rules interact with one another or when scans are executed in sequence. The dastlite system employs a layered approach to inter-scan rule dependency management, which includes dynamic rule prioritization, stateful context tracking, and conditional execution logic. These mechanisms collectively ensure that the rule engine operates efficiently, avoids redundant or conflicting findings, and adapts to evolving scan environments.

Dynamic rule prioritization is the foundation of inter-scan dependency management in dastlite. This process involves assigning a priority level to each rule based on its dependencies, the likelihood of false positives, and the impact of its findings on subsequent rules. For example, a rule that identifies authentication vulnerabilities may be prioritized higher than one that detects misconfigurations in static assets, as the former often has cascading effects on the latter. This prioritization is implemented through a weighted graph structure, where each node represents a rule and edges represent dependencies or interactions between rules. The graph is continuously updated during scan execution based on real-time feedback from the scanner, ensuring that the priority levels remain relevant to the current scan context. This approach not only optimizes performance but also minimizes the risk of redundant or overlapping findings.

Stateful context tracking is another key mechanism in dastlite’s inter-scan dependency management. Unlike traditional DAST tools that treat each scan as an isolated event, dastlite maintains a persistent state across multiple scans, allowing it to track the progress of rule execution and the outcomes of previous scans. This state is stored in a structured format, such as a JSON document or a relational database, and includes information about the current scan phase, the status of each rule, and the context-specific data required for conditional execution. For instance, if a scan begins with an authentication step, the state will record the session token and user roles, which can be used to determine which rules are applicable in subsequent phases. This tracking enables dastlite to avoid re-scanning the same endpoints unnecessarily and to apply rules that depend on previous findings, such as detecting authorization bypasses after identifying authentication vulnerabilities.

Conditional execution logic is the third pillar of dastlite’s inter-scan dependency management. This logic allows rules to be executed only under specific conditions, based on the state of the scan or the results of previously executed rules. For example, a rule that checks for insecure HTTP headers may be conditional on the presence of an active session, while a rule that identifies SQL injection vulnerabilities may depend on the successful identification of a database endpoint. These conditions are defined using a combination of static configuration and dynamic runtime data, ensuring that rules are applied only when relevant. The dastlite system uses a declarative syntax for defining these conditions, similar to the structure of JSON Web Tokens (JWTs), which allows for flexible and scalable rule dependencies. This logic is further enhanced by the use of event-driven architecture, where changes in scan state trigger the execution of dependent rules, ensuring that the rule engine remains responsive to evolving conditions.

The implementation of dynamic rule prioritization, stateful context tracking, and conditional execution logic in dastlite is supported by a robust infrastructure of data structures and algorithms. The weighted graph used for rule prioritization is implemented using adjacency lists, with each node containing metadata about the rule’s dependencies, impact score, and execution order. This structure allows for efficient traversal and updating during scan execution. For stateful context tracking, dastlite employs a combination of in-memory caching and persistent storage, ensuring that scan state is preserved across restarts and distributed nodes. The conditional execution logic is realized through a finite state machine (FSM), where each state represents a phase of the scan and transitions are triggered by specific events or conditions. This FSM is augmented with a rule dependency resolver that dynamically adjusts the execution order based on the current state and the availability of required context.

One concrete example of inter-scan rule dependency management in action is the detection of session fixation vulnerabilities in a multi-phase scan. In this scenario, the initial phase of the scan identifies authentication endpoints and establishes session tokens. The stateful context tracking mechanism records these tokens, which are then used in subsequent phases to execute rules that check for session fixation. A rule that identifies session fixation vulnerabilities may depend on the presence of a valid session token and the ability to manipulate it, which are both tracked in the scan state. The conditional execution logic ensures that this rule is only applied after the initial authentication phase has completed, preventing false positives or unnecessary scans. Additionally, dynamic rule prioritization assigns a higher priority to this rule based on its dependency on the session token, ensuring that it is executed before rules that may be affected by the findings of session fixation.

Another example involves the coordination of rules for detecting insecure API endpoints and misconfigurations in cloud storage. In a scan targeting a web application with an API backend, the initial phase may identify endpoints that expose sensitive data. A rule that checks for insecure API endpoints may be prioritized higher than one that detects misconfigurations in cloud storage, as the former often has more immediate security implications. However, if the scan reveals that certain endpoints are not properly secured, the stateful context tracking mechanism will record this information and use it to conditionally execute a rule that checks for misconfigurations in the cloud storage associated with those endpoints. This dependency ensures that the scan remains focused on relevant areas while avoiding redundant checks.

The integration of these mechanisms into dastlite’s rule engine is further enhanced by the use of machine learning models for predictive prioritization and context adaptation. These models analyze historical scan data to identify patterns in rule execution and dependencies, allowing the system to dynamically adjust priorities and conditions based on past performance. For instance, if a particular rule has consistently produced false positives in certain environments, the model may recommend lowering its priority or modifying its conditions to reduce unnecessary execution. This predictive approach ensures that the rule engine remains adaptive and efficient, even as scan environments evolve.

In summary, inter-scan rule dependency management in dastlite is achieved through dynamic rule prioritization, stateful context tracking, and conditional execution logic. These mechanisms work in concert to ensure that rules are executed in the correct order, under the right conditions, and with the necessary context, thereby enhancing the accuracy and efficiency of scan results. The implementation of these features is supported by a combination of data structures, algorithms, and machine learning models, enabling dastlite to handle complex dependencies across multiple scans while maintaining consistency and coherence in its findings.

### Rule Result Deduplication and Contextual Filtering

The core challenge in rule engine execution within a DAST runner is not merely the application of rules but the management of their outcomes—particularly the duplication of findings and the contextual filtering of false positives. Rule Result Deduplication and Contextual Filtering are critical components that ensure the output of the scan remains both accurate and actionable. These mechanisms operate at multiple layers, from the initial detection of vulnerabilities to the final aggregation of results, ensuring that each reported issue is unique, relevant, and properly contextualized within the target environment.

Rule result deduplication begins with the identification of duplicate findings across different rules or rule invocations. A common source of duplication is when multiple rules trigger on the same vulnerability type but apply to overlapping or identical conditions. For instance, a rule detecting SQL injection via a specific pattern may overlap with another rule that identifies similar injection vectors through syntactic analysis. Without deduplication, these findings could be reported as separate issues, leading to redundancy and confusion in the final report.

To address this, dastlite employs a multi-step deduplication process that operates at both the rule level and the instance level. At the rule level, the system applies a set of pre-defined deduplication rules that compare the outputs of different rules based on their severity, type, and context. For example, if two rules both detect an SQL injection vulnerability in the same endpoint, the system will evaluate whether they are semantically equivalent by comparing their payload patterns, HTTP methods, and response structures. If deemed equivalent, one of the findings is marked as a duplicate and excluded from the final output.

At the instance level, deduplication is more granular and focuses on identifying identical or highly similar findings across different rule invocations. This is achieved through a combination of hash-based comparison and semantic similarity analysis. For each detected issue, dastlite generates a unique identifier based on the endpoint URL, HTTP method, response content, and rule metadata. These identifiers are then compared to existing entries in a global deduplication cache. If a matching identifier is found, the system determines whether the new finding is a true duplicate or a variation that requires separate treatment.

The deduplication process also incorporates contextual filtering to further refine the results. Contextual filtering evaluates the environment in which a vulnerability occurs, including factors such as authentication state, user roles, and application behavior. For example, a rule that detects an insecure direct object reference (IDOR) might produce false positives when applied to endpoints that are not accessed by unauthenticated users. By integrating contextual information from the DAST runner’s crawling and authentication phases, dastlite can filter out such false positives, ensuring that only relevant findings are reported.

One specific mechanism used in contextual filtering is the application of rule-specific metadata that defines the conditions under which a finding should be considered valid. For instance, a rule detecting cross-site scripting (XSS) might include metadata specifying that the vulnerability is only valid if the endpoint accepts user input in a query parameter and does not sanitize it properly. During execution, dastlite evaluates these conditions against the actual request and response data, marking findings that fail to meet the criteria as false positives.

Another key aspect of contextual filtering is the use of dynamic thresholds based on the target environment. For example, a rule detecting excessive HTTP request rates might produce false positives in environments with high traffic or asynchronous API calls. dastlite allows administrators to define threshold values for such rules, specifying how many requests must be detected within a given timeframe before a finding is considered valid. This approach ensures that the system adapts to the specific behavior of the target application, reducing the likelihood of false positives.

In addition to static and dynamic thresholds, dastlite employs machine learning models to enhance contextual filtering. These models are trained on historical scan data and manually validated findings, allowing them to identify patterns that distinguish true vulnerabilities from false positives. For instance, a model might learn that certain types of endpoints—such as those handling file uploads—are more likely to contain vulnerabilities related to insecure file storage, while others are less likely to do so. By applying such models during execution, dastlite can dynamically adjust the sensitivity of rules based on the context of each request.

The deduplication and contextual filtering mechanisms in dastlite are further supported by a robust logging and reporting framework that tracks the origin and evolution of each finding.
